# SW-013C.2A — Configuration-Only Port Materialization: Findings Report

**Status: Implementation NOT performed. This investigation found that the work order's own premise — that the Hornet/Retaliator ports in question are absent from the StarBreaker geometry export — is factually incorrect for the confirmed cases (Hornet Mk II, Retaliator). A simpler, safer, already-partially-designed fix exists and is recommended instead of the "configuration-only port materialization" architecture as specified. Awaiting Chief Architect direction before any code is written.**

> **✅ CERTIFIED FINDING — implemented by SW-013C.2B.** This report's root-cause correction (a classification-translation gap, not an absent-geometry gap) and its recommendation (activate the existing Module taxonomy design rather than build a new merge architecture) were both approved and implemented exactly as recommended. See `docs/SW-013C.2B-Module-Taxonomy-Activation-Report.md` for the full implementation record.

## Why This Stops Before Implementation

SW-013C.2's own root-cause report (the direct predecessor to this work order) concluded that `hardpoint_weapon_center` and `hardpoint_nose_cone` are absent from the StarBreaker `--dump-hierarchy` export entirely — a claim inherited from `docs/ADR/ADR-014-Configurable-Slot-Architecture.md`. This work order's entire architecture (a new "configuration-only port" concept, a new canonical-identity scheme, a new provenance model, an additive merge stage) is built on that premise.

**Direct re-investigation this session — running the real `ShipNormalizer` against the actual checked-in raw export files — shows the premise is wrong.** Both ports **are** present in `doc.loadout`, each with a real, factory-installed entity:

```
hardpoint_weapon_center -> entity: "UMNT_ANVL_S5_Cap_Mk2"   (Hornet Ghost Mk II)
hardpoint_nose_cone     -> entity: "ANVL_F7_Mk2_NoseCap"    (Hornet Ghost Mk II)
hardpoint_front_module  -> entity: "AEGS_Retaliator_Module_Front_Base"  (Retaliator)
hardpoint_rear_module   -> entity: "AEGS_Retaliator_Module_Rear_Base"   (Retaliator)
```

They are excluded later, for a completely different and much more specific reason: **their factory component's DataCore category (`Module` for the Cap/Rotodome/module-bay family, `Misc` for the nose cap) has no entry anywhere in SFM's classification-translation tables**, so `classifyPort` can never assign them a `portType`, and a port with no `portType` is excluded by design ("No portType on raw node — cannot classify safely"). Confirmed live, this session, via the real normalizer:

```
"No classification translation for \"UMNT_ANVL_S5_Cap_Mk2\": No translation rule for DataCore category \"Module\" — left unclassified rather than guessed."
"No classification translation for \"ANVL_F7_Mk2_NoseCap\": No translation rule for DataCore category \"Misc\" — left unclassified rather than guessed."
"No classification translation for \"AEGS_Retaliator_Module_Front_Base\": No translation rule for DataCore category \"Module\" — left unclassified rather than guessed."
```

**This exact gap was already found, and its fix already designed — just never authorized.** `ADR-014` Decision D5 states plainly: *"`AttachDef.Type: 'Module'`... has no entry today in `CATEGORY_TO_PORT_TYPE` or `PLAYER_USABLE_COMPONENT_TYPES`. Per the same principle ADR-011 established for `Turret`, this is a translation-boundary gap to fix at that boundary... not a caller-side workaround."* Its companion document, `docs/ModuleTaxonomyProposal.md`, works out the actual fix in detail (new `Module` port type, compatibility exclusively swap-group-derived, never a generic Size/Type sweep) — and explicitly states: *"Status: design only... No implementation authorized."* It also flags one genuinely open, unresolved **product** question that blocks implementation either way (see §4).

Building this work order's "configuration-only port materialization" architecture on top of an incorrect premise would mean solving a problem that mostly doesn't exist in the assumed shape, while leaving the real gap (a missing classification rule) unfixed — and would create exactly the kind of **second, parallel topology authority** this codebase's own architecture has consistently avoided (ADR-014 D1: "one generic mechanism... never a per-ship special case"). Once the classification gap is eventually fixed, these ports would start flowing through the ordinary Normalizer pipeline as real `factory-geometry` ports — colliding conceptually, if not by id, with whatever synthetic "configuration-only" rows this job would have built for them today.

## Findings, By Objective

### Root cause (corrected)

Not "port absent from geometry export." **Port present in geometry export, with a real factory-installed component, but excluded during classification because its DataCore category (`Module`/`Misc`) has no translation rule.** This is a single, generic, already-anticipated gap — not a Hornet-specific or Retaliator-specific defect, and not evidence of two competing topology authorities. It is one authority (the Normalizer) with one incomplete lookup table.

### Objective 4 — Hornet center-cap / filler semantics (answered directly, with evidence)

> "Determine from authoritative data whether the cap is: a factory-installed physical component / a selectable configuration alternative / a non-operational geometry/filler object / or absent from the current export."

**It is a factory-installed physical component**, confirmed directly in the raw export (`entity: "UMNT_ANVL_S5_Cap_Mk2"`, a real DataCore entity class, not geometry-only). It is **also** a selectable-configuration-alternative situation at the same time — ADR-014's own confirmed swap group (`$ANVL_Hornet_Mk2_Center`) lists real armed alternatives (`ANVL_Hornet_F7CM_Mk2_Ball_Turret` and others) a Commander can choose instead. **It is not absent from the export, and it is not purely cosmetic/non-operational geometry** — it has no children of its own, but it is a real, factory-shipped DataCore entity occupying a real port. Per this job's own stated rule: *"If the filler is an authoritative installed item, preserve it as installed state."* **The resulting rule: once classified, the Cap should appear as this port's real Factory/Installed item — not Intentional Empty, not a fabricated Ball Turret** — with the Ball Turret and other alternatives available as Target choices exactly like any other weapon-mount swap.

The nose cap (`ANVL_F7_Mk2_NoseCap`, category `Misc`) is a real factory-installed component by the same evidence, but **its own swap-group / alternative-component authority remains unresolved** — ADR-014's own "Open investigations" section already flagged this: the nose cap's referenced item had no populated `Tags` for the Swap Group Resolver to key off at the time of that investigation, and this session's direct check of `generated-data/configurable-slots.runtime.json` confirms it: zero entries for any "nose" port anywhere in the Ghost's configurable-slot catalog. Fixing the `Misc` classification gap would make the nose cap visible and correctly represented as an installed filler — but would **not**, on its own, give a Commander any real alternative component to install there. That is a separate, still-open data question (a live DataCore tag investigation), not a code defect.

### Objective 6 corpus item 2 — "One Hornet Mk I variant" (premise does not apply)

Traced directly: the Hornet Mk I (`ANVL_Hornet_F7A_Mk1`) has **no defect of this kind at all.** Its nose and center mounts (`hardpoint_class_4_nose`, `hardpoint_class_4_center`) already exist as ordinary, correctly-classified `WeaponTurret` ports — factory-armed with a real Nose Turret (`ANVL_Hornet_F7A_Mk1_Nose_Turret`) and a real, already-gunned Ball Turret (`ANVL_Hornet_F7A_Mk1_Ball_Turret`, itself carrying two real installed lasers on `turret_left`/`turret_right`). These already render correctly in Ship Management today, with zero code changes. The Mk I is not a second instance of this bug — it is evidence the *general* weapon-turret pipeline works correctly; only the Mk II generation's "may ship uncapped or capped" configurability triggers the classification gap, because the Mk II's factory default specifically is the non-weapon Cap, not a turret.

### Objective 7 — Vanguard (preliminary, not certified)

Not investigated in depth this session, since implementation was not authorized. Recorded per the work order's own instruction to "investigate but do not force into scope without evidence": the Vanguard's four exclusive nose weapon positions are a distinct RSI-manufacturer design (not an Anvil Cap/Rotodome-style swap point), and nothing found this session suggests they share the `Module`/`Misc` classification gap — but this has not been directly verified against the Vanguard's own raw export and should not be assumed either way before a real check.

## Objection Conditions Found (Not "Stop Conditions" — no explicit list in this WO, but analogous)

This work order names one explicit stop trigger: *"STOP if parentage cannot be resolved deterministically"* (Objective 2). That trigger was never reached, because the premise requiring a parentage-resolution scheme (ports absent from geometry, needing synthetic attachment) does not hold for the confirmed cases. The condition that did halt this job is more fundamental: **the architecture being requested solves a different problem than the one that actually exists**, and an already-designed, simpler, lower-risk alternative sits one document away, explicitly waiting on a product decision this job is not authorized to make unilaterally.

### The one open product question blocking either path

`docs/ModuleTaxonomyProposal.md`'s own unresolved question, verbatim: whether an empty/unconfigured Module-category slot should count toward ship readiness —

1. **Strict** — an empty Configurable Slot counts as a readiness gap, like any other empty port.
2. **Permissive** — readiness-neutral by default, since CIG's own factory default is legitimately "a passive cosmetic fairing," not a Commander decision that matters operationally.

This materially changes what a Commander sees on every affected ship's readiness percentage and Decision Summary the moment it ships — it is a product call, not an engineering one, and neither ADR-014 nor its companion proposal resolves it. This job cannot responsibly pick one and proceed.

## Recommendation

1. **Do not build the "configuration-only port materialization" architecture as specified** for the Hornet Mk II / Retaliator cases — the simpler, already-designed classification-translation fix (ADR-014 D5 / `ModuleTaxonomyProposal.md`) is the correct, minimal, single-authority-consistent repair once the Chief Architect resolves the readiness-participation question above.
2. **Keep the general "configuration-only materialization" concept on the shelf, not discarded** — it remains a legitimate, real need for any future case where a port is *genuinely* absent from `doc.loadout` (unlike the cases confirmed here). This session did not find such a case, but did not exhaustively search for one either.
3. **The Hornet Mk I does not belong in this certification corpus** — it already works. Recommend Objective 6 be re-scoped once implementation is authorized.
4. **The nose cap's own swap-group data remains a genuinely open, separate data question**, independent of the classification-translation fix — fixing classification alone will not surface a nose-turret alternative to the Commander; that requires further live DataCore investigation this job did not perform.
