# Engineering Risk Register — Configurable Slot Architecture

> **Status: design only.** Companion to `docs/ADR/ADR-014-Configurable-Slot-Architecture.md`. Documents risk only — no implementation, no mitigation code authorized here.

| ID | Risk | Current Behavior | Likelihood | Impact | Mitigation | Future Migration Strategy |
|---|---|---|---|---|---|---|
| R-001 | Swap-group membership is established by component-side `AttachDef.Tags` co-occurrence only; no populated port-side declaration (`RequiredPortTags` or equivalent) was found during the ADR-014 investigation | Every confirmed swap group in this design is `confidence: 'tag-co-membership'` (see `SwapGroupSpecification.md`) — real, live-verified, but one-sided | Medium | Medium — a future CIG patch could add a genuinely unrelated component that happens to reuse a tag string, silently widening an eligible set | Validation rules in `SwapGroupSpecification.md` §7-8 (entity-class cross-check, default-must-be-self-member, cross-slot tag reuse logged); confidence tier is structurally visible, never hidden | If a genuine port-side declaration is later found (R-003), promote matching slots to `confirmed-bidirectional` without a model change — additive, no migration needed |
| R-002 | The `$`-prefix convention (restricted/grouped family vs. ordinary broadly-mountable item) is an *observed* pattern from a small sample, not a CIG-documented rule | Not encoded as a hard filter anywhere (see `SwapGroupSpecification.md` §3 — deliberately not used for normalization, since the real `ANVL_Hornet_Center` group has no `$` prefix at all) | Low | Low — a counter-example would reduce confidence in the *observation* as documentation, not corrupt any resolved data, since the prefix is never load-bearing in the algorithm | None needed — the observation is documentation-only | N/A |
| R-003 | A richer per-port `SItemPortDef` (`Types`/`MinSize`/`MaxSize`/`RequiredPortTags`) may exist elsewhere in the DataCore record graph for combat-relevant ports; only proven **absent** from one location (the ship's own top-level `SItemPortContainerComponentParams.Ports[]`, confirmed sparse — 5 utility-only entries on the Hornet Mk II) | Unknown/unexplored beyond that one location | Unknown | Low (upside risk — a missed corroborating signal, not a correctness bug) | Listed as an Open Investigation in ADR-014's Readiness Review | Would only ever *add* confidence to existing slots, never require a breaking model change (see R-001's own migration note) |
| R-004 | **Persisted Component Reference Drift.** `useFleetStore.ts`'s `migrate()` validates persisted-record *shape* (`isValidPersistedHardpoint`/`isValidPersistedFleetAsset`/`isValidPersistedBuild`) but never re-resolves a persisted component name/entityClass against the *current* generated catalog | Directly observed and root-caused during the ADR-004/SW-009A Amendment 1 relic investigation: a hand-typed seed fixture value ("Snowblind") persisted with a one-character casing mismatch against the real catalog ("SnowBlind") went completely undetected by every existing migration/validation check, because none of them compare component *identity*, only record *shape*. Confirmed the mismatch produced a duplicate, unclassified selector entry rather than a loud failure — an honest-degradation outcome, not a crash, but a silent one | Medium — proven to occur for hand-authored dev-seed data; not proven (and not disproven) for real Commander-persisted data reaching this state via a legitimate historical path | Medium — a Commander whose persisted data drifted from the current catalog would see an unclassified/duplicate option rather than an error, which is easy to miss and was in fact reported as a Commander-visible defect | None implemented — explicitly out of scope for this design sprint (`MigrationStrategy.md`'s own "no data migration" Non-Goal). The concrete instance already found was fixed at the source (`src/data/seed.ts` correction, ADR-004/SW-009A Amendment 1, commit `62fedc4`) — this register entry is about the *general, still-open* architectural gap, not the one instance already resolved | A future identity-validation pass in `migrate()` (or a separate, explicit "reconcile persisted component references against the current catalog" maintenance step) is the natural fix — deliberately not designed here, since it is a persistence-layer change orthogonal to Configurable Slots and deserves its own dedicated review rather than being folded into this feature's scope |

| R-007 | **Physical Port Graph identity is also scoped, not global** (SW-010B Certification Report §9, discovered while fixing the equivalent bug on the configuration side — see R-008). `canonicalMerge.ts`'s "attach vs. synthesize" decision matches against `PhysicalPortFact[]`, a flat `Set<string>` of bare port names built from the real geometry export | Two physically distinct real ports sharing a bare name (e.g. two different `turret_left` mounts, confirmed to exist — the real Retaliator has 5) cannot currently be told apart by the attach/synthesize check; each would be attributed to "the" physical port rather than its own specific mount | Medium — confirmed the underlying data shape exists broadly (§3.2 of the certification report); not yet measured how often it changes the attach/synthesize *outcome* specifically | Low-Medium — a slot may be mis-labeled `geometry-and-configuration` vs `configuration-only`, not lost or duplicated (Configurable Slot identity itself is unaffected, since `ConfigurableSlot` construction doesn't depend on this check's outcome) | None implemented — explicitly out of scope for SW-010B (`scripts/configurableSlots/`'s own boundary excludes `PhysicalPortFact`'s source, by design) | Widen `PhysicalPortFact` to carry the same full ancestor-path identity `DefaultLoadoutConfigurationEntry.ancestorPortNames` already uses (R-008's fix) — same pattern, applied to the geometry side, in a future phase |

## Risk scoring key

- **Likelihood / Impact:** Low / Medium / High / Unknown, qualitative — no formal scoring model is proposed by this document.
- Every risk above is either **documented-and-monitored** (no code change) or **already mitigated by a validation rule specified in a companion document** (`SwapGroupSpecification.md`) — none require new implementation to be "handled" at the design stage; they require visibility, which this register provides.
