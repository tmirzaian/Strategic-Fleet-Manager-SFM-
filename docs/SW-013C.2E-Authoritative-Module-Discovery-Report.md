## Objective 1 — Hornet Mk II Nose Turret: Stop (Discovery Complete, Implementation Requires New Capability)

**Exhaustive re-investigation, not a repeat of the prior "no topology exists" conclusion.** A real Mk II nose turret exists: `ANVL_Hornet_F7C_Mk2_Nose_Turret` (confirmed via direct live `dcb query` — category `Turret`, subtype `CanardTurret`, size S3, 2 real `WeaponGun`/S2 child ports: `hardpoint_weapon_S1_left`/`_right`). It is a confirmed member of a real, tight (2-member, category **A-confirmed**) swap group, `ANVL_Hornet_Mk2`, discovered on `hardpoint_weapon_nose` — a real, physically-positioned hardpoint (confirmed via its own `bone_to_world` transform data) present on the Ghost's (`ANVL_Hornet_F7CS_Mk2`) own 3D model.

**How CIG models it:** the base F7CM_Mk2/F7A_Mk2 variants factory-ship `hardpoint_weapon_nose` occupied (with the older `ANVL_Hornet_F7A_Nose_Turret`); the Ghost, F7C_Mk2, and F7CR_Mk2 all leave it factory-**empty** — a real design choice (stealth/recon-lineage variants forgo the offensive nose turret), not a missing mount point. This is confirmed by the geometry node itself being present, positioned, and identical across variants.

**Why it bypasses current discovery logic:** SFM's entire import pipeline creates a `Port` **only** from an occupied `doc.loadout` entry. A real, physically-present hardpoint that a specific ship variant ships factory-empty is invisible to the normalizer regardless of how much confirmed compatibility data exists for the identical port name on a sibling ship's own occupied use of it.

**Why this is not implemented:** the fix requires a genuinely new capability — synthesizing a real `Port` (with its own real, static child structure) on a ship that never occupies it, sourced from a sibling ship's own already-imported structure — that exists nowhere in this codebase today, and touches the cross-ship-unaware core normalizer or a new post-processing graft step spanning several interdependent generated files (`ports.json`, `components.json`, `factory-loadouts.json`, `installed-loadouts.json`, `target-builds.json`). Building this now, for one confirmed case, under an already-large work order, is exactly the "speculative implementation" the mission's own Stop Conditions warn against. **Stop condition invoked: "Discovery would require speculative implementation."** Locked in as a deliberate regression test (`hornetNoseTurretDiscovery.test.ts`) so a future mission that adds this capability updates the test alongside it, never silently.

## Objective 2 — EMP Compatibility Refinement (Implemented)

**REP-VS (`AEGS_EMP_Sentinel_S4`) is genuinely compatible** — confirmed via: (a) a tight, 2-member `AEGS_EMP_Device` swap group (category A/B-confirmed, not an overly-broad sweep), and (b) REP-VS is factory-shipped on a real ship elsewhere in the game (the Aegis Vanguard Sentinel). Compatibility filtering was **not** incomplete.

**The real issue was display formatting bypassing canonical presentation.** `appendSwapGroupOptions` (the shared helper behind Module/EMP/Quantum Dampener/confirmed-group Missile Rack options) used its own ad hoc `"{name} — S{size}"` label, set unconditionally — diverging from `fullComponentCatalog.ts`'s own established canonical convention, `"{name} — {category}, S{size}"`, used only when a real disambiguation need exists. Fixed: `appendSwapGroupOptions` now derives the candidate's own canonical category label (`swapGroupCategoryLabelFor`, a small explicit map: Module/EMP/Quantum Dampener/Missile Rack/Bomb Rack — the only categories any swap-group branch can ever offer) and formats every option identically to the established convention. REP-8 and REP-VS now both render correctly; REP-VS reads `"REP-VS EMP Generator — EMP, S4"`.

## Objective 3 — Retaliator Module Family Discovery (Implemented)

Confirmed live: `hardpoint_front_module`/`hardpoint_rear_module` each already carry a real, **category A-confirmed** swap group (`AEGS_Retaliator_Module_Front`/`_Rear`) with 4 members apiece:

| Entity | Real displayName | Role |
|---|---|---|
| `..._Front_Base` / `..._Rear_Base` | "Retaliator Unladen Front/Rear Module" | Factory default — already classified since SW-013C.2B |
| `..._Front_Cargo` / `..._Rear_Cargo` | "Retaliator Cargo Front/Rear Module" | Real: 1 non-player-relevant Door-type cargo-lift child port only |
| `..._Front_Bomber` / `..._Rear_Bomber` | "Retaliator Ordnance Front/Rear Module" | Real: a genuine nested rack-mount port, `hardpoint_torpedo_launcher_fore`/`_rear` (MinSize 3–MaxSize 9, accepts MissileLauncher/BombLauncher/WeaponGun-Rocket) |
| `..._Front` / `..._Rear` (bare) | none (`@LOC_PLACEHOLDER`) | Real record, no usable display name — see Objective 6 |

**Root cause of invisibility:** these 4 useful variants are never factory-referenced by any checked-in raw-data ship (only `AEGS_Retaliator.json` exists — no Bomber/Cargo trim files), so SFM's component-catalog generator's narrow, raw-data-scoped discovery path never saw them — the same shape of gap SW-013C.2B's report already documented for `UMNT_ANVL_S5_Rotodome_Mk2`.

**Fix:** `scripts/generateComponentCatalog.ts` gained `CONFIRMED_SUPPLEMENTARY_ENTITY_CLASSES` — a small, individually-verified list of 6 entity classes added directly to Path 1's own entity set, resolved via the exact same already-fetched bulk DataCore field maps (zero new StarBreaker spawns, zero change to Path 2's own category-allowlist sweep). All 6 resolve into the full catalog; the 2 bare "Unladen" duplicates are then correctly excluded from the shipped runtime subset by the pre-existing "no fabricated display name" rule — not a bug, and not a loss, since the factory default already represents the real, named Unladen state (see Objective 6).

No classification-pipeline changes were needed — the Front/Rear ports were already Module-classified since SW-013C.2B, and the swap-group-only picker mechanism (SW-013C.2D) already routes Module ports correctly; this was purely a missing-catalog-record gap.

## Objective 4 — Retaliator Payload Propagation (Partially Complete — Cargo/Unladen Trivially Satisfied, Ordnance Requires New Capability)

**Cargo → Cargo topology:** the real DataCore record has no player-relevant child port at all — only a `Door`-type cargo-lift mechanism. There is no further "cargo topology" to propagate; module selection alone completes it. **Already correct, nothing further needed.**

**Unladen → Empty topology:** the real record's only child is a `hardpoint_module_oc` occlusion-culling helper (no `Types` at all — not player-relevant). **Already correct, nothing further needed.**

**Ordnance → Bomb/Torpedo topology:** the Ordnance module's own confirmed child port (`hardpoint_torpedo_launcher_fore`/`_rear`) is real, but structurally novel: it is itself a swappable **rack-mount** port (like `hardpoint_torpedorack`), not a fixed-size payload slot — and it is never factory-occupied anywhere in the raw-data corpus, so (a) it has never been imported as a `Port` at all (the same Objective-1-shaped gap), and (b) its own `MinSize: 3, MaxSize: 9` range plus its triple `Types` (MissileLauncher/BombLauncher/WeaponGun-Rocket) don't fit the single-size, single-category port model every existing compatibility mechanism assumes — resolving it correctly (rather than guessing one category or one size) would require extending the compatibility engine itself, not just reusing it. **Stop condition invoked: "Discovery would require speculative implementation."** This is a second, independently-evidenced instance of the same underlying gap Objective 1 found — reinforcing that it is a real, recurring architectural limitation worth its own dedicated future mission, not a one-off.

## Objective 5 — Specialized Discovery Audit (Reconnaissance Only, Per Instruction)

Ran a systematic `normalizationWarnings` sweep across the entire certification fleet (Ghost, Eclipse, Retaliator, Guardian Qi, Mantis, Warlock). Findings, filtered to exclude routine structural/cosmetic noise (cockpit MFDs/displays, self-destruct charges, docking-collar fuel ports, personal habitation items — fire extinguishers, personal lockers, personal weapon racks):

**Top recommendation for a future mission: Countermeasure Launchers (DataCore category `WeaponDefensive`).** Every single ship in the certification fleet carries real, currently-invisible chaff/flare/decoy/noise launcher equipment (`hardpoint_countermeasure_launcher_left`/`_right` or equivalent) — a real, ship-level, Commander-relevant survivability system, consistently unclassified across the entire fleet. This is the clearest, highest-leverage, best-evidenced gap this audit found.

Other findings, explicitly **not** recommended (habitation/cosmetic, not ship-system equipment): personal storage lockers (`Cargo`-category but genuinely personal, not ship cargo capacity), personal weapon racks and fire extinguishers (`Usable`/`WeaponPersonal` — interior habitation props), cockpit display screens/MFDs (`Display` — UI chrome, not equipment), self-destruct charges (`SelfDestruct` — flavor, not configurable equipment), docking-collar fuel ports (`DockingCollar` — structural).

Per this objective's own explicit instruction, **no implementation was made** — this is reconnaissance only, reported for a future work order's own scoping decision.
