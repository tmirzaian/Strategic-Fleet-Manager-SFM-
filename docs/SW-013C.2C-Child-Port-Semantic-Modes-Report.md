# SW-013C.2C — Child-Port Semantic Modes: Implementation Report

Operation: Swamp Fox · Classification: Architecture Generalization (Amendment) · Priority: Critical Commander Validation Blocker

**Status: Implemented, tested, live-validated (7/7 live checks, including save + genuine reload). Not committed — awaiting Chief Architect review and Commander visual certification.**

## Summary

Generalized the existing component-owned child-port architecture (`componentOwnedChildSlotSpec`/`withComponentOwnedChildSlots`, previously covering only missile racks and mining modules) to carry an authoritative `mode` — `'payload-array'` or `'independent-equipment'` — and added a third family, turret weapon slots, as the first `'independent-equipment'` case. Mode is derived from certified entity-class/category data, never from child count or display name, per the amendment's Governing Rule. The Hornet Ghost Mk II's Center mount, when a Commander targets the Ball Turret alternative, now exposes its two real weapon-mount children ("Weapon Slot 1"/"Weapon Slot 2") as fully independent ports: separate Target, separate compatibility, separate readiness, separate inventory demand, no sibling-target coupling, no aggregation. Missile racks and mining modules are unchanged — same code paths, same behavior, confirmed via regression.

A real, previously-latent rehydration bug was found and fixed along the way (see "Root Cause Found During Live Proof" below) — without it, the required "save and reload" live proof would have silently failed in production for this specific case, even though every unit test that stopped short of a genuine module reload passed.

## Governing Rule — How Mode Is Determined

`componentOwnedChildSlotSpec(entityClass)` (`src/utils/componentOwnedSlots.ts`) is the one authority. It checks, in order, three independently-certified data sources, and only ever returns a spec for an entity class explicit allowlists or generated tables recognize:

1. Mining module count (`getMiningModuleSlotCount`) → `{ label: 'Module', mode: 'payload-array' }`
2. Missile rack slot data (`getMissileRackSlotSpec`) → `{ label: 'Missile', mode: 'payload-array' }`
3. Turret weapon slot data (`getTurretWeaponSlotSpec`, new) → `{ label: 'Weapon', mode: 'independent-equipment' }`

None of these infer mode from quantity or name. A parent with exactly two child ports is a rack, a turret, or neither, purely by which of the three certified tables recognizes its entity class — never by "it has 2 children so it must be a turret."

## Objective 1 — Reused vs. Not Reused

**Reused as-is** (per the amendment's explicit instruction): parent-to-child structural derivation (`withComponentOwnedChildSlots`), stable child identity (slot-position-based), Factory/Installed/Target separation, the persistence materialization skeleton in `saveMissionConfiguration`, and rendering plumbing (`prepareCanonicalHardpoints`, `buildPortTree`).

**Not generalized** (kept mode-gated): `withMissileRackAggregation` remains hard-gated to `spec.label === 'Missile'` — confirmed pre-existing, not touched. Weapon children are never folded into an aggregate "2× S3 Weapon" row. Readiness and inventory-demand computation were already per-row/per-name (`computeHardpointStatus`, `calculateComponentAvailability`) with no rack-wide concept to begin with, so nothing needed a new gate there — but Objective 6's parent-replacement logic (which previously assumed "same slotLabel means same lineage") required an explicit mode branch, described below.

## Objective 2 — Turret Weapon-Slot Data

**`scripts/generateTurretWeaponSlots.ts`** (new) — derives weapon-slot specs from checked-in `raw-data/*.json` StarBreaker exports (same ground-truth source as the missile-rack generator), scoped to `CONFIRMED_TURRET_ENTITY_CLASSES` (`ANVL_Hornet_F7CM_Mk2_Ball_Turret`, `ANVL_Hornet_F7CM_Mk2_Ball_Turret_Bespoke` — individually confirmed, not a category sweep). `EXCLUDED_CHILD_CATEGORIES` (`MissileLauncher`, `Missile`, `Bomb`, `BombLauncher`) keeps the turret's own nested missile rack out of the weapon-slot count — a deliberate, documented scope boundary (see Remaining Gaps).

Confirmed run output:
- `ANVL_Hornet_F7CM_Mk2_Ball_Turret` (found in `ANVL_Hornet_F7CM_Mk2.json`): 2 weapon slots, size S3.
- `ANVL_Hornet_F7CM_Mk2_Ball_Turret_Bespoke` (found in `ANVL_Hornet_F7CM_Mk2_Heartseeker.json`): 2 weapon slots, size S4.

The size difference between the two turret variants was the deciding evidence for the parent-replacement orphan test (Objective 6).

**`src/generated/turretWeaponSlots.ts`** (new) — browser-side loader (`getTurretWeaponSlotSpec`), mirrors `missileRackSlots.ts`'s exact pattern.

**`generated-data/turret-weapon-slots.json`** (new, generated) — the two confirmed specs.

## Objective 5/6/7 — Independent Sibling Targets, Parent Replacement, No Aggregation

**`src/utils/componentOwnedSlots.ts`** — `ComponentOwnedSlotSpec` gained a required `mode: 'payload-array' | 'independent-equipment'` field.

**`src/store/useFleetStore.ts`** (`saveMissionConfiguration`) — the materialization loop now looks up each parent's **previous effective spec and prior per-position child targets** from the correctly-scoped `existingRows` (not `referenceRows`, which may belong to a different, non-active build — see Errors below), via two hoisted maps populated only in the `EXISTING`-build branch. For a parent whose new spec is `'independent-equipment'` and whose target just changed (`swapped === true`), each child position is explicitly resolved rather than left to fall through the old shared has-check:

- Carry the prior sibling's own target forward **only if** the previous spec was also `'independent-equipment'` **and** its size matches the new spec's size (same-size turret-to-turret swap preserves a still-compatible selection).
- Otherwise reset that position to empty (`'—'`) — an incompatible-size swap (e.g. S3 Ball Turret → S4 Bespoke variant) never silently carries over a now-wrong-size weapon; it's diagnosed as orphaned by simply starting empty, never guessed.

Payload-array (missile rack, mining module) behavior is untouched — same three-way branch, same rebuild-from-scratch-on-swap semantics as before this mission.

**No-aggregation**: `withMissileRackAggregation`'s pre-existing `spec.label !== 'Missile'` gate already excludes `'Weapon'`-labeled children from folding — confirmed via test, not modified.

## Stop Condition — Confirmed Not Triggered

The amendment's Stop Condition ("the current runtime model represents all repeated child ports only as a homogeneous quantity and therefore cannot preserve independent equipment identities without a broader model change") does not apply. Mining-module children were already proven to work as independent, un-aggregated rows under the existing architecture before this mission touched anything — `withMissileRackAggregation`'s label-gate was already the mechanism keeping them from being folded. Turret weapon slots needed a third data source and a `mode` field, not a new model.

## Root Cause Found During Live Proof — Reload/Rehydration Bug (Fixed)

The required live proof ("save and reload mixed weapon selections") initially failed on reload only: raw persisted `localStorage` JSON was correct, but after a genuine store rehydration the two synthesized weapon-child rows vanished from `useFleetStore`'s own state entirely — not a display bug.

**Root cause**: `reconcileBuildHardpoints` (`src/utils/fleetAssetReconciliation.ts`, EWO-043) decides which parent slot labels are "component-owned" (and therefore exempt from normal template reconciliation, carried through verbatim) by checking `componentOwnedChildSlotSpec(t.factoryEntityClass)` — the **template's factory identity**. Every existing family (missile racks, mining heads) always ships component-owning from the factory, so this was sufficient. The Hornet's Center mount does not: its factory item is an ordinary Cap, and it only becomes component-owning once a Commander **targets** the Ball Turret onto it. Keyed on factory identity alone, the reconciler never recognized "Center Weapon" as component-owned, so on the next rehydration its weapon children matched nothing in the static template and were silently quarantined.

**Fix**: `componentOwnedParentSlotLabels` now also qualifies a slot label when the **previously-persisted row** at that same label was itself already component-owning under its own effective (target-first) identity — `componentOwnedChildSlotSpec(oldParent.targetEntityClass ?? oldParent.factoryEntityClass)`. This only ever adds recognition for a port that was already correctly component-owned last session; it cannot cause a normal port to be misclassified, since an ordinary Cap that was never swapped has no old row satisfying that check either.

Confirmed via a fast `vi.resetModules()`-based reproduction (bisected with the fix stashed out and restored) that this exact test fails without the fix (`expected undefined to be 'Omnisky IX Cannon'`) and passes with it — this is now a permanent regression test (see Files Changed).

Separately, the existing "save and reload" test in the new suite never called `vi.resetModules()` before its re-import, so it was silently re-testing the same already-initialized module and never exercised rehydration at all — a false-negative gap. Fixed in place; the corrected version is what caught (and now guards) the bug above.

- The Ball Turret's own **nested missile rack** (`hardpoint_missile_rack` → `MRCK_S04_ANVL_Hornet_F7CM_Mk2_Turret`, 8 children, confirmed present in raw data) is deliberately excluded from the weapon-slot spec by `EXCLUDED_CHILD_CATEGORIES`.
