## Root Cause (Not Symptoms)

**The Nose Turret and Center Ball Turret are not missing due to any bug in Strategic Fleet Manager's importer, normalizer, tree builder, or Ship Workspace rendering. They are missing because the raw StarBreaker geometry export SFM's import pipeline reads (`doc.loadout`) never contains a node for either port in the first place.** Both ports have no factory-installed component by default — an empty attachment point — and StarBreaker's own `--dump-hierarchy` export tool silently omits any port matching that shape. SFM's `ShipNormalizer` (`src/normalizer/shipNormalizer.ts`) walks exactly what `doc.loadout` gives it; there is nothing to classify, filter, or drop, because the nodes never arrive as input. **This is a confirmed, prior finding, not a new discovery** — it was fully investigated and documented in `docs/ADR/ADR-014-Configurable-Slot-Architecture.md` (SW-008C Revision 1, dated the same day as this investigation) via live `dcb query` against the actual `Data.p4k`. That ADR's own Non-Goals section states plainly: **"No implementation of any kind — this document and its companion deliverables are the design only."** SW-011A subsequently implemented a read-only Configurable Slot badge/inspection panel, but only for ports that already have a real `Hardpoint` row — it never gained a mechanism to materialize a *new* row for a port Authority 1 never produced. The result: the two turret slots are fully known to SFM's own generated data (high-confidence, tagged, with real alternative components enumerated) but have no visual representation anywhere in Ship Management, because no `Hardpoint` row for them has ever existed to render.

**"Previous topology certification" did not certify this as working.** No commit, ADR, or test in this repository ever claimed the Nose/Center ports were rendered in the tree. ADR-014 explicitly certified the *mechanism that discovers* these ports (Authorities 2/3, the Swap Group Resolver design) — not their presence in Ship Management's port tree, which was always out of that ADR's stated scope ("No change to... any Commander-visible UI").

## Objective 2 — Runtime Artifact Validation

Per the work order's own instruction ("If missing here: Stop. The issue is upstream."):

- **Hornet nose turret / center ball turret exist?** Split result, re-confirmed live this session:
  - `generated-data/ports.json` (Authority 1 / the tree's actual data source): **absent**.
  - `generated-data/configurable-slots.runtime.json` (Authority 2+3, a separate DCB-query pipeline): **present** — `hardpoint_weapon_center` only (category `A-confirmed`, 7 eligible components); `hardpoint_nose_cone` is absent from *both* artifacts (ADR-014's own "Open investigations" already flagged this: the nose slot's referenced item had no populated `Tags` for the Swap Group Resolver to key off, so even the configurable-slots generator has nothing to report for it — a step further upstream than Center).
- **Parent hierarchy correct?** N/A for the missing rows (no row exists to have a parent); `hardpoint_weapon_center`'s own recorded `parentPortName` is `null` (a top-level port), consistent with its physical position.
- **Configurable slot metadata present?** Yes, for Center (`A-confirmed`); no, for Nose (never resolved by the Swap Group Resolver at all).
- **Port Authority metadata present where applicable?** Not evaluated — `getComponentOwnedPortConstraint` is keyed by an owning mount's own entityClass and a real `portName`; with no `Hardpoint` row, Port Authority resolution never runs for this port at all. Moot until a row exists.

**Two artifacts disagree about the same ship's own topology.** This is itself one of the work order's own Stop Conditions (see below).

## Stop Conditions Triggered

Per the work order's own explicit instruction — **"Do not continue with speculative repairs"** — the following were discovered and this investigation stopped before any implementation:

1. **"Runtime artifacts contradict normalized data."** `configurable-slots.runtime.json` (built from live DCB queries against Authorities 2/3) asserts `hardpoint_weapon_center` is a real, `A-confirmed` port on the Hornet Ghost Mk II. `ports.json`/`shipFactoryTemplates` (the Normalizer's own output, "normalized data") contains no such port. These are two independently-generated artifacts describing the same ship's topology and disagreeing about whether a specific port exists.
2. **"Multiple ship classes share the same underlying defect."** Re-confirmed live, independent of ADR-014's own prior claim: the Aegis Retaliator exhibits the identical pattern — `hardpoint_front_module`/`hardpoint_rear_module` are `A-confirmed` in `configurable-slots.runtime.json` (4 eligible components each) and completely absent from `ports.json`. ADR-014's own live tag sweep additionally names the RSI Scorpius, Argo MOTH, and the Hornet Mk I/base family (which has its **own** separate swap-group tag, `ANVL_Hornet_Center`, whose alternatives explicitly include `ANVL_Hornet_F7C_Nose_Turret` and `ANVL_Hornet_F7A_Mk1_Nose_Turret` — a genuine Nose Turret component, further evidence this mechanism generalizes and is not Hornet-Mk-II-specific). A fix scoped only to "the Ghost" would not be a real fix — it would need to touch the shared Normalizer/Importer pipeline, which by construction affects every previously-imported ship.

Both conditions independently mandate stopping before implementation, per the work order's own explicit text.

## Objective 7 — Operation Swamp Fox Review

No identifiers were changed — no implementation occurred. If and when a repair is authorized, the two viable directions and their identity implications are:

- **Merge Authority 2/3 into the main Normalizer walk**, so `hardpoint_weapon_center`-class ports materialize as real `Hardpoint` rows going forward. This would mint *new* port/hardpoint ids (following the existing `${shipId}-port-${sourcePath}` scheme, additive) for previously-nonexistent rows — it would not change any existing port's id, since the affected ports currently have no id anywhere in the system. Existing persisted Fleet Assets (a Commander's already-materialized Ghost) would need the existing `reconcileBuildHardpoints` self-heal mechanism (`src/utils/fleetAssetReconciliation.ts`, the same mechanism `saveMissionConfiguration` already uses to append newly-appearing canonical ports without discarding a Commander's saved Loadout) to pick up the new row on next load — this is an established, already-proven pattern, not a new risk.
- **Regenerate the runtime artifacts from a corrected export** (if StarBreaker itself can be coaxed into including empty-attachment ports, or if SFM's own importer is extended to read Authority 2 directly). Same identity implications as above — additive only.

Neither direction requires renaming, re-keying, or reinterpreting any existing identifier. **No destructive migration is anticipated for either direction**, but this is a preliminary assessment for the Chief Architect's planning purposes, not a certified migration strategy — that certification is this job's own explicit Non-Goal until a repair path is chosen.
