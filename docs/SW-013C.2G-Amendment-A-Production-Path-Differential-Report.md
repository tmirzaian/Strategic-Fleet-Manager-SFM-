# SW-013C.2G — Amendment A: Production Path Differential Analysis

**Status:** Root cause identified — not a compatibility-engine defect. One genuine, unrelated data-consistency bug found and fixed along the way.
**Commit:** HOLD — awaiting Commander re-verification and Operational Certification.

## 1. Finding

The Nose Turret **is** correctly discoverable and selectable on the production Ghost Mk II runtime path. It was not found because the Commander's reported "Current selector" (`Intentional Empty` / `ANVL F7 Mk2 NoseCap`) is the **Nose Cone** row's own dropdown, not the separate **Nose Weapon** row's dropdown. These are two distinct ports on two distinct rows in the loadout tree — confirmed live, on the same running dev server, against the exact pre-existing seed Ghost fixture (`/ship-workspace/ghost`, no Add Ship flow, no injected state):

```
Nose Cone dropdown options:   ["Intentional Empty (—)", "ANVL F7 Mk2 NoseCap"]
Nose Weapon dropdown options: ["Intentional Empty (—)", "Anvil Hornet Mk II S3 Nose Turret — Gimbal Mount, S3",
                                "Anvil Hornet Mk II S2 Nose Turret — Gimbal Mount, S3"]
```

The first line is an exact match for the Commander's reported "Current selector." The second line is the Nose Weapon row, sitting a short scroll away, already showing both confirmed swap-group turret candidates. Candidate discovery for the dormant port has been working the entire time; the "FAIL" was pointed at the wrong row.

## 2. Why the two rows are easy to conflate

The two ports are architecturally unrelated but sit in the same physical position on the hull, and the tree currently gives no visual cue that they're related:

- **Nose Cone** (`hardpoint_nose_cone`) — `equipmentGroup: "Modules"`, a real, always-occupied Module port (the physical nose cap/fairing).
- **Nose Weapon** (`hardpoint_weapon_nose`) — `equipmentGroup: "Weapons"` / `groupLabel: "Pilot Weapons"`, the dormant, materialized turret mount this mission added.

Because they render under entirely different top-level tree sections (Modules vs. Weapons), they can be far apart in the expanded tree with nothing connecting them. The original work order's own expected UI sketch (Objective 3) implicitly groups them under one shared "Nose Position" heading:

```
Nose Position
├── F7 Mk II Nose Cap
└── Mk II S3 Nose Turret
    ├── Weapon Slot 1
    └── Weapon Slot 2
```

The current implementation never built that shared heading — both rows exist, are individually correct, and are individually tested, but nothing in the tree visually asserts "these two belong to the same physical position." **Recommendation, not yet implemented:** group Nose Cone and Nose Weapon (and any future materialized dormant port sharing a real port's physical position) under a shared position-level heading, using the `positionLabel` field `dormantHardpoints.ts` already carries (`positionLabel: 'Nose'`) but which nothing currently reads for display grouping. This is a Ship Workspace tree-layout change, broader than this mission's own scope — flagging for Commander direction rather than implementing speculatively.

## 3. Investigation path (for the record)

Three independent, genuinely distinct production-path reproductions were run before reaching the finding above, since the report's own "restarted the dev server, result unchanged" detail warranted ruling out several real candidate causes first, not just re-checking the already-tested fresh-asset path:

1. **The pre-existing seed 'ghost' fixture directly** (`src/data/seed.ts`'s `id: 'ghost', name: 'F7C-S Hornet Ghost Mk II'`) — architecturally distinct from the mission's own real imported ship (`hornet-f7cs-mk2-imported`, catalog display name "Hornet F7CS Mk2"), and the far more likely ship a Commander's own pre-seeded dev fleet actually contains. Its Hardpoint rows are built by a **third**, independent row-construction path — `useFleetStore.ts`'s `buildCanonicalSeedCustomBuilds` — that duplicates `materializeFleetAsset`'s row shape rather than reusing it, and had never been updated to carry `isDormant`/`dormantDonorShipEntityClass` onto its own rows (§4).
2. **An old, pre-feature `localStorage` save reconciling forward** — simulating a Commander whose browser last touched the app before this feature shipped (a dev-server restart does not clear browser `localStorage`). Reconciliation correctly appends the new dormant port and its candidates.
3. **A live browser check against the actual running dev server**, navigating directly to the seed Ghost's workspace with no synthetic setup at all — the check that produced the exact match in §1.

All three reproduce the Nose Weapon row correctly offering the turret. None reproduce the reported failure — because the reported failure was never in the Nose Weapon row to begin with.

## 4. One real bug found and fixed (not the reported symptom, but worth keeping)

While reproducing scenario 1 above, the seed fixture's raw stored Hardpoint row for Nose Weapon was found to be missing `isDormant`/`dormantDonorShipEntityClass` entirely — `buildCanonicalSeedCustomBuilds` (`src/store/useFleetStore.ts`) never received the same two-field passthrough already added to `materializeFleetAsset` and `overlayCanonicalHierarchy` during the base SW-013C.2G mission. This is a genuine, real inconsistency in the raw store data for every seed ship's custom build.

**Why it never caused a visible defect:** every rendering path (`ShipWorkspacePrototype.tsx`'s "Manage Loadout" view included) reads hardpoints through `src/utils/canonicalHardpointPreparation.ts`'s `prepareCanonicalHardpoints`, which calls `overlayCanonicalHierarchy` — re-deriving `isDormant`/`dormantDonorShipEntityClass` fresh from the current canonical template by `slotLabel` on every render, regardless of what the raw stored row carries. The display was always correct; only the raw, unrendered store row was wrong. This could still matter for any future consumer that reads `useFleetStore.getState().hardpoints` directly without going through `prepareCanonicalHardpoints` (e.g. an export, a report, a readiness calculation added later without going through the shared preparation step) — fixed for correctness and consistency with the two other row-construction sites, confirmed via `tsc --noEmit` and the full regression suite.

**Fixed:** `src/store/useFleetStore.ts`, `buildCanonicalSeedCustomBuilds`'s non-structural row branch now includes `isDormant: slot.isDormant, dormantDonorShipEntityClass: slot.dormantDonorShipEntityClass`, mirroring the structural-row exclusion already established elsewhere (dormant ports are never structural, so the structural branch is correctly left untouched).
