# SW-013C.2F Amendment B — Dynamic Payload Selection Functional Recovery: Addendum Report

Operation: Swamp Fox · Classification: Functional Defect Remediation · Priority: Release blocker for topology certification

**Status: Root-caused, fixed, tested, and live-verified — two distinct defects, one shared root cause. Not committed — Commit: HOLD, per standing instruction.**

## Exact handler / reconciliation root cause

The defect lives entirely in `src/pages/ShipWorkspacePrototype.tsx`'s `renderLensCells`, in the `MANAGE_LOADOUT` branch's read-side computation of what a row's own New Target picker currently displays. Two distinct bugs, both specific to aggregate payload rows (missile racks, bomb racks — anything rendered through `withMissileRackAggregation`), share one root cause: **a mismatch between where a Commander's pending pick gets WRITTEN and where the picker's displayed value gets READ back.**

### Bug 1 — the displayed value reverted immediately after picking

Amendment A's `commitNewTarget` fan-out (already correct) writes a Commander's aggregate-row pick to every real child slotLabel (`hp.missileAggregate.childSlotLabels`) — e.g. `"Torpedorack — Bomb Slot 1"` … `"Slot 20"` — never to the aggregate row's own synthetic slotLabel (`"Torpedorack — Bomb"`, which has no real Hardpoint and never should receive a write). The READ side, however, still computed the displayed value as `desiredTargets[hp.slotLabel] ?? hp.targetItem` — using `hp.slotLabel`, which for an aggregate row IS that same synthetic label. Since nothing is ever written there by design, this lookup was always `undefined`, silently falling through to `hp.targetItem`.

For a rack that was ALSO just swapped in the same session (the reported scenario — pick a new rack, then pick a payload for it), `hp.targetItem` on the freshly-synthesized aggregate row is itself the empty sentinel (`'—'`), because its real children were only just materialized and never saved — confirmed live: the picker didn't merely show the OLD payload, it showed `'—'`, exactly matching the Commander's own "Intentional-empty normalization collision" hypothesis, though the actual mechanism is the key mismatch above, not a lookup-failure fallback.

### Bug 2 — stale targets migrated between different rack geometries

Found while building the required "parent replacement" test (20×S3 with a payload assigned, swapped to 1×S10): fixing Bug 1 alone surfaced a second, independent defect. A rack's real per-slot children are regenerated with POSITION-based slotLabels (`"<rack> — Bomb Slot 1"` … `"N"`) — a fresh 1×S10 generation's own single child is *also* named `"Torpedorack — Bomb Slot 1"`, the exact same string the OLD 20×S3 generation's own first child used. `desiredTargets["Torpedorack — Bomb Slot 1"]` from the prior generation was never cleared on rack swap, so the new S10 child's picker showed the stale Thunderball Bomb selection from the old S3 generation — a real violation of the Amendment's own explicit negative control ("No stale targets migrate between different rack geometries").

## The fix

Both fixed in `commitNewTarget`/`renderLensCells`, `src/pages/ShipWorkspacePrototype.tsx`:

1. **Read side (Bug 1):** for an aggregate row, resolve the displayed pending value from its own real children's slotLabels instead of the synthetic one — `commitNewTarget`'s fan-out always writes the identical value to every child in one state update, so any one child with a pending entry represents the whole rack. `hp.targetItem`/`hp.targetEntityClass` themselves are left completely untouched (still the aggregate's own correctly-computed last-saved baseline from `makeMissileAggregateRow`), so `isEdited`'s existing "pending vs. last-saved" comparison stays meaningful rather than becoming a tautology.
2. **Write side (Bug 2):** whenever a RACK's own target changes (never an aggregate row's own fan-out, which this same function still performs unchanged), `commitNewTarget` now clears every pending entry already recorded under that rack's own child-label prefix (`"<rack> — "`) before writing the new target — guaranteeing a freshly-swapped rack's own children always start from a clean slate. A harmless no-op for every ordinary, childless port.

Both fixes are entirely generic — gated only on `hp.missileAggregate` (truthy for any payload-array aggregate row: missile rack, bomb rack, or any future rack family reusing `withMissileRackAggregation`) and on slotLabel string prefixes, never on ship name, entity class, or rack size. No Eclipse-specific or MSD-313-specific code exists anywhere in the fix.

## Why existing tests passed despite the live failure

Every pre-existing aggregate-row test (including Amendment A's own new Finding 1 matrix) drove the flow to completion — select rack, select payload, **click Save**, then inspect the STORE's real hardpoints (`useFleetStore.getState().hardpoints`) — never the picker's own displayed `value` in between. `commitNewTarget`'s write side was already correct after Amendment A, so the store ended up right regardless of what the UI displayed along the way; `saveMissionConfiguration` reads `desiredTargets` directly by its own real keys, never through the same buggy read-side computation `renderLensCells` used for display. The bug was entirely invisible to any test that didn't specifically assert on the picker's own `.value` immediately after a pick and before a save — which no existing test did. Bug 2 (stale migration) was invisible for the same reason plus an additional one: no existing test performed a rack-swap-with-payload-already-assigned-then-swap-again sequence at all.

## Regression test that demonstrably fails before the fix

Confirmed via `git stash`-style before/after: with only Amendment A's `commitNewTarget` write-side fix applied (Bug 1's read-side fix reverted), the exact scenario from the required matrix —

```
select 20xS3 rack for the Eclipse's Torpedorack → select Thunderball Bomb for the aggregate row
```

produced `bombInput.value === '—'` instead of `'Thunderball Bomb'` immediately after the pick. After restoring the fix, the same test passes. This exact assertion is now permanent: `src/pages/__tests__/sw013c2fAmendmentB.test.tsx`, first test in the file.

## Missile and bomb: one shared root cause

Yes — confirmed directly. Both share the identical `withMissileRackAggregation`/`makeMissileAggregateRow` mechanism (gated on `spec.label === 'Missile' || spec.label === 'Bomb'`, the same single code path since SW-013C.2D), and the fix lives entirely in the one shared `renderLensCells`/`commitNewTarget` pair every aggregate row — missile or bomb — flows through. The permanent regression suite proves this directly: the MSD-313 missile case, the existing multi-child missile rack, and all three Eclipse bomb rack sizes are covered by the same two fixes with no per-family branching.
