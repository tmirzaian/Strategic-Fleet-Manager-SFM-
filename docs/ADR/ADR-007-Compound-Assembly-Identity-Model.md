# ADR-007 — Compound Assembly Identity Model

- **Status:** Accepted
- **Date:** 2026-07-14

## Context

EWO-019B introduced a presentation-only grouping layer (`groupPortTree()`) on top of the normalized port tree, but could not group Weapons separately from Manned/Remote Turrets, and could not give Eclipse's Quantum Drive a real Jump Module child — because the *data* those decisions need had already been discarded during normalization, not merely rendered flatly.

Direct comparison of `generated-data/ports.json` against real raw StarBreaker exports (Eclipse, Cutlass Black, Valkyrie, Corsair, Gladius) found the exact loss point: `ShipNormalizer`'s `walk()` (`src/normalizer/shipNormalizer.ts`) drops any node `classifyPort()` excludes — including a mount/turret assembly node whose own DataCore category never resolves (not a genuine "irrelevant node" like a door or a seat) — and silently re-parents that node's children to its own parent, discarding the mount/turret's identity and position entirely. Two further, narrower classification gaps compounded this for the Quantum Drive case specifically: `component-metadata-catalog.json` represents "no DataCore SubType" two different ways for the same fact (`null` for most entries, the literal string `"UNDEFINED"` for a minority, including the Eclipse fixture's own Jump Drive) and `classificationTranslator.ts`'s exact-match rule only recognized one; and DataCore's real `WeaponMount`/`WeaponControl` category (confirmed via Valkyrie's door guns) had no translation rule mapping it to the existing `WeaponGun` canonical type at all.

## Decision

**Two general-purpose normalizer corrections**, applying to every ship, not just the five proof vessels:
1. `classificationTranslator.ts`'s subtype matching now treats `null` and `"UNDEFINED"` as the same "no subtype" fact (`normalizeSubtype()`).
2. A new `WeaponMount`/`WeaponControl` → `WeaponGun` translation rule, verified against all 12 real `WeaponMount` catalog entries (a single consistent subtype).

**A new, conservative assembly-role model** (`src/normalizer/assemblyRole.ts`): `Port` gains `sourceEntityClass` (the raw CIG entity class mounted at a port), `assemblyRole` (one of `DIRECT_WEAPON_MOUNT | GIMBAL_MOUNT | WEAPON | MISSILE_RACK | MISSILE_SLOT | MISSILE | MANNED_TURRET | REMOTE_TURRET | QUANTUM_DRIVE | JUMP_MODULE | GENERIC_MOUNT | UNKNOWN`), and `isStructural`. The role is derived from the entity class's own DataCore naming convention (`Mount_Gimbal_*`, `WeaponMount_*`, a `Turret` token combined with `Remote`/`Nose` tokens for disambiguation) — never from a port/hardpoint name, which EWO-019B already proved unreliable (a Valkyrie wing port literally named `turret_gun` hosts a plain gimbal mount; `hardpoint_turret_door_*` hosts a fixed, non-turret mount). `GENERIC_MOUNT`/`UNKNOWN` are legitimate, expected outcomes when the evidence doesn't support a specific role — never forced.

**Structural node preservation**: `ShipNormalizer.walk()` now checks, for any node `classifyPort()` would exclude, whether it has a real, included descendant. If so, the node is preserved as a `Port` with `isStructural: true` — a stable id, a real `parentPortId`/`childPortIds` chain, a real position-derived `displayName` — but it is never added to `relevantForFactory`, so it can never receive a factory/installed/target component assignment of its own. A node with no included descendant (a door, a seat, a light) is still dropped exactly as before.

**Business-calculation safety without new filtering logic**: a structural `Hardpoint`'s `factoryItem`/`installedItem`/`targetItem` are all set to the existing `"—"` empty-port sentinel at materialization time (`src/utils/fleetAssetMaterializer.ts`). Both `calculateBuildProgress()` (`src/utils/buildProgress.ts`) and `calculateMissionPackage()` (`src/engine/logistics/missionPackage.ts`) already exclude any hardpoint whose `targetItem === '—'` from their required/procurement sets — a structural row is automatically invisible to readiness and procurement with zero new filtering code, the same mechanism that already correctly excludes any other empty, non-required port.

**Presentation**: `groupPortTree()`'s top-level synthetic headers now use `assemblyRole` (via `topLevelGroupLabel()`, `src/data/shipDefinitions.ts`) to sort ports into a fixed, Chief-Architect-approved player-facing order (`TOP_LEVEL_GROUP_ORDER`: Core Systems, Detection/Navigation, Weapons, Manned Turrets, Remote Turrets, Ordnance, Utility Systems, Support Systems) — a stable sort, so any category this mission doesn't define stays visible in its original position rather than being forced into an approximate bucket. `LoadoutPortTree.tsx`/`MissionComposer.tsx` render a structural row with neutral `"—"` cells and no logistics/validation badges or editable target input, and render every group header in the table's own base typeface (no `font-display`) — weight/case/spacing/color differentiate it instead, matching the table's own pre-existing `<thead>` convention.

## Consequences

- Verified live against all 5 proof vessels: Eclipse's Quantum Drive now genuinely parents its Jump Module (Explorer resolved correctly, no longer mislabeled "Jump Drive" carrying the Quantum Drive's semantic weight); Eclipse's two weapon mounts render as real "Left Weapon"/"Right Weapon" positions instead of two identical "Class 2" rows; Cutlass Black's real manned turret and Valkyrie's two manned turrets plus two remote turrets (and Corsair's, whose own DataCore entity classes turned out to literally contain "Manned"/independently confirming the model without any Corsair-specific tuning) all separate correctly from plain weapon mounts — using the exact same code path, no ship names anywhere in the classification logic.
- Gladius's golden fixture remains 14/14 passing, byte-for-byte stable except for the new (larger, more honest) proof-group-wide grouping applied uniformly.
- Determinism preserved: two full `npm run import:ships` runs produce byte-identical `generated-data/*.json` output.
- Known remaining limitation: a handful of real entities (e.g. Valkyrie's own `ANVL_Valkyrie_Turret_Top`/`_Bubble`, Cutlass Black's `DRAK_Cutlass_SCItem_Turret_Black`) are still absent from `component-metadata-catalog.json` entirely — the structural-node mechanism papers over this for *hierarchy* purposes, but a future catalog-coverage pass (out of this mission's scope) would let these mounts carry their own real display name/grade instead of the `GENERIC_MOUNT` positional label alone.
- Missile rack/slot/missile hierarchy required no change: direct raw-export inspection (Eclipse's torpedo rack, Cutlass Black's pylons) confirmed the source genuinely models a rack's numbered attach points as the slot *and* the missile assignment in one node — there is no separate "slot" entity being flattened away, so the existing 2-level Rack → Missile structure is already a truthful representation, not a simplification.
