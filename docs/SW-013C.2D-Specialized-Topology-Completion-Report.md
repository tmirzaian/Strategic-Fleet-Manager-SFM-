# SW-013C.2D — Specialized Topology Completion & Workspace Save Accessibility: Implementation Report

Operation: Swamp Fox · Classification: Architecture Completion · Priority: High

**Status: Implemented, tested, live-validated (11/11 live checks). Not committed — awaiting Commander Certification.**

## Summary

Completed the remaining architectural gaps the Architectural Certification Fleet exposed: a persistent Save/Discard action bar for the Ship Workspace, the Hornet Ghost Mk II's Nose topology investigation (no authoritative topology exists — documented, not fabricated), the Eclipse's mission-rack compatibility fix (a real cross-ship false-positive, fixed at its authoritative root), exposure of the Eclipse's three confirmed Bomb Rack alternates, and canonical support for the Electronic Warfare equipment family (EMP, Quantum Dampener/Interdiction) across the Guardian Qi, Mantis, and Avenger Warlock. Two genuine, previously-latent bugs were found and fixed along the way — a false "Invalid Target" on a certified swap-group selection, and a stale-identity aggregation defect — both locked in by regression tests.

## Objective 1 — Persistent Workspace Save Actions

**`src/pages/ShipWorkspacePrototype.tsx`** — a `fixed inset-x-0 md:left-64 bottom-0` action bar, rendered only while `commanderIntent === 'MANAGE_LOADOUT' && pendingChangeCount > 0` (hidden entirely otherwise). It is a second entry point to the exact same `handleSaveChanges`/`handleDiscardChanges` handlers and `desiredTargets` state SW-008D already established — never a parallel save path. Shows the live pending-change count and the reviewed Loadout's name. `z-10`, deliberately below `TargetComponentPicker`'s dropdown popover (`z-20`), so a New Target picker opened near the bottom of the viewport always renders above the bar, never hidden beneath it; a trailing spacer div reserves real document height so the bar never permanently covers the table's own last rows. The existing panel-header Save/Discard controls (SW-008D) are unchanged and still present — this supplements, not replaces them. SW-013C.1's guarded Loadout-switch protection is untouched and confirmed still enforced with the bar present.

## Objective 2 — Hornet Mk II Nose Topology: No Authoritative Topology Exists

Investigated directly against the real raw StarBreaker export and the generated port/swap-group data:

- `ports.json`: the Ghost's `hardpoint_nose_cone` port (factory item `ANVL_F7_Mk2_NoseCap`) has `childPortIds: []`.
- Raw export (`ANVL_Hornet_F7CS_Mk2.json`): the Nose Cap is the last entry in `doc.loadout`, parented directly to the ship entity itself; no other entry names it as a parent.
- `configurable-slots.runtime.json`: no swap-group entry exists at all for `hardpoint_nose_cone` on this ship — no confirmed alternate component, unlike the Center mount's own real `$ANVL_Hornet_Mk2_Center` group.

**Conclusion: no child topology and no swap-group data exist for this port — a genuinely different situation from the Center mount, not an oversight.** Related, out-of-scope finding: the base (non-stealth) F7CM Mk2 variant has a real `hardpoint_weapon_nose` port hosting `ANVL_Hornet_F7A_Nose_Turret` — a different physical port that does not exist on the Ghost's own hull at all, confirmed via the Ghost's own raw export lacking it entirely. No implementation was made; nothing in the current port/swap-group data justifies one.

## Objective 3/4 — Eclipse Mission Rack Compatibility + Alternate Rack Discovery

**Root cause (Objective 3):** the Eclipse's own factory rack (`MRCK_S09_AEGS_Eclipse`) and the Aegis Retaliator's own racks (`MRCK_S09_AEGS_Retaliator_Fore`/`_Rear`) share the identical DataCore category (`MissileLauncher`/`MissileRack`) **and** the identical catalog `size` field (9 — the accepted torpedo class, not a rack-family identifier). The generic size/category compatibility sweep (`src/data/componentCatalog.ts`) could never distinguish them — this is what let the Retaliator's rack appear selectable on the Eclipse.

**Authoritative fix:** `ShipWorkspacePrototype.tsx`'s `newTargetOptionsFor` now checks whether a `'Missile Rack'`-typed port's own certified swap group exists (`configurableSlotFor`). When one does — the Eclipse's own confirmed `Eclipse_BombRack` group — target options are scoped to **only** that group's real members. When none exists (the overwhelming majority of ships, including the Hornet Ghost, whose own rack ports have no confirmed group), the pre-existing generic sweep is used unchanged — this is what preserves SW-008C's own cross-ship Hornet-to-Fury rack-swap test. The distinction is derived entirely from whether real swap-group data exists for that specific port, never from ship identity.

**Objective 4 (live-confirmed, not from display names):** ran a live `dcb query` against each of the Eclipse's four swap-group members. All three Bomb Rack alternates are real:

| Entity | Ports confirmed | Display name |
|---|---|---|
| `BMBRCK_S10_AEGS_Eclipse` | 1 × S10 | Aegis Eclipse 1xS10 Bomb Rack |
| `BMBRCK_S05_AEGS_Eclipse` | 4 × S5 | Aegis Eclipse 4xS5 Bomb Rack |
| `BMBRCK_S03_AEGS_Eclipse` | 20 × S3 | Aegis Eclipse 20xS3 Bomb Rack |

Each embedded slot count in its own display name matched the live DataCore record exactly — confirmed independently, not trusted from the name alone.

**`scripts/generateBombRackSlots.ts`** (new) — mirrors `generateMissileRackSlots.ts` exactly, scoped to the real `BombLauncher`/`BombRack` DataCore family (a genuinely different component family per that generator's own established scope boundary — never merged into the missile-rack table). Discovered and resolved 13/14 real `BombLauncher`/`BombRack` entities catalog-wide (Retaliator, Gladiator, Spirit, Starlancer, Castillo, Eclipse); one (`MRCK_S03_TEMP_BOMB`) honestly skipped — non-uniform port sizes, a placeholder-named test entity, not fabricated. Output: `generated-data/bomb-rack-slots.json`, loaded via new `src/generated/bombRackSlots.ts`.

**`src/utils/componentOwnedSlots.ts`** — Bomb Rack wired in as a fourth component-owned family (`label: 'Bomb'`, `mode: 'payload-array'`), alongside Mining Module, Missile Rack, and Turret Weapon Slots.

**`src/utils/missileRackAggregation.ts`** — `withMissileRackAggregation`'s gate widened from `label === 'Missile'` to also include `'Bomb'` (same single-selection ordnance-rack presentation the Chief Architect's own "Payload Systems" grouping treats as one class); `makeMissileAggregateRow` generalized from hardcoded `'Missile'` strings to `spec.label`-derived ones (identical output for every existing missile rack). `src/pages/MissionComposer.tsx`'s mirrored `makePreviewAggregateRow` received the same fix.

**Two real bugs found and fixed while proving this end-to-end:**

1. **False "Invalid Target" on a certified swap-group selection.** A Bomb Rack candidate's own translated category (`BombLauncher` → "Bomb Launcher") never matches a Missile-Rack-typed port's own type — the generic compatibility check flagged a Commander's correct, swap-group-offered selection as invalid. Fixed by adding `CompatibilityIdentityHint.knownCompatibleEntityClasses` (`src/data/componentCatalog.ts`) — when a candidate's entityClass is a member of the destination port's own confirmed swap group, it is authoritatively valid regardless of the generic sweep's conclusion. Threaded through `computeHardpointStatusWithValidation`'s `HardpointStatusIdentity` and populated at both the save-time (`useFleetStore.ts`) and rehydration/reconciliation (`fleetAssetReconciliation.ts`) call sites via the new `swapGroupEligibleEntityClassesFor` (`src/generated/configurableSlots.ts`) — the same real swap-group data the picker itself reads, so a reload can never disagree with what was just saved. Zero behavior change for any port with no confirmed swap group.
2. **Aggregate row derived its shape from stale, installed-based identity.** `withMissileRackAggregation` used `currentEntityClassOf` (installed-first) to decide the aggregate's own label/count — correct for the "swapped" check that decides whether old children are stale, but wrong for a target-only edit that was never physically installed (an entirely ordinary Manage Loadout state): the aggregate kept showing the OLD 3-slot Missile Rack's shape even though the real, correctly-materialized 20 Bomb Slot children were already present. Fixed with a target-first identity resolution scoped to aggregation display only (`node.hardpoint.previewTargetEntityClass ?? node.hardpoint.targetEntityClass ?? currentEntityClassOf(...)`) — `withComponentOwnedChildSlots`'s own children-preservation logic was not touched.

## Objective 5/6 — Electronic Warfare Topology + Canonical Taxonomy

Confirmed via direct catalog inspection: exactly two previously-unclassified DataCore categories cover this entire family — `EMP` (6 real entities catalog-wide: REP-8/REP-VS EMP Generator, TroMag Burst Generator ×3, Magstrand EMP Generator) and `QuantumInterdictionGenerator` (4 real entities: Captor QD, Burke QD, Tidelock QD, Reynie QED). No separate "Electronic Warfare" or "Interdiction" DataCore category exists — those are the English names for the same two categories, not additional gaps. Both are small and entirely clean (zero cosmetic/irrelevant members), justifying whole-category translation rules rather than an entity allowlist (unlike Module's 13-entity category, which had real contamination).

A real finding while investigating the Mantis: its own `hardpoint_interdiction_device` port resolves to exactly **one** real item-port relationship (`QED_WETK_S03_Reynie`, "Reynie QED") — not two. A QED is fictionally a combined dampener + interdiction device; no second, fabricated "Snare" port was added to satisfy the Commander Acceptance checklist's phrasing. Also confirmed the trap the mission's own governing rule warns against: `QED_RSI_S03_Scorpius`'s displayName is "Tidelock **QD**" despite its `QED_`-prefixed entityClass — category, not name or prefix, is the only reliable signal.

**`src/normalizer/classificationTranslator.ts`** — two new whole-category rules: `EMP → 'EMP'`, `QuantumInterdictionGenerator → 'QuantumDampener'`.

**`src/engine/types/equipmentGroup.ts`** — new `'ElectronicWarfare'` group.

**`src/normalizer/portClassifier.ts`** — `EMP`/`QuantumDampener` canonical types both map to the new group.

**`src/data/shipDefinitions.ts`** — `topLevelGroupLabel` routes `ElectronicWarfare` into the existing "Support Systems" section (alongside Relays/LifeSupport — the Chief Architect's own preferred placement). `compatibilityTypeFor` gained an early check (mirroring the existing `SalvageModule` pattern) so EMP and Quantum Dampener keep distinct per-row type strings (`'EMP'`, `'Quantum Dampener'`) despite sharing one display section.

**`ShipWorkspacePrototype.tsx`** — EMP/Quantum Dampener ports route through the same swap-group-only picker mechanism Module already uses (never the generic sweep, which has nothing to offer them anyway since neither category is in `CATEGORY_TO_PORT_TYPE`). This activated a real find: the Avenger Warlock's EMP port has a genuine confirmed swap group (`AEGS_EMP_Device` — `AEGS_EMP_Device_S4` default, `AEGS_EMP_Sentinel_S4` real alternate), so it is not "no upgrade path" after all; Guardian Qi's Dampener and the Mantis's QED have no confirmed group today and correctly show no alternates — target defaults to the factory item, future compatibility requires no schema change if a group is ever discovered.
