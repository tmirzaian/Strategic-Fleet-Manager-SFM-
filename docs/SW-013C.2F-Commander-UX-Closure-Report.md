# SW-013C.2F — Commander UX Closure & Specialized Presentation Refinement: Implementation Report

Operation: Swamp Fox · Classification: Commander Experience Polish (Phase 1) · Priority: High

**Status: All seven objectives implemented, tested, and live-verified. Not committed — awaiting Commander Operational Certification.**

## Summary

Every objective in this work order turned out to have a real, fixable root cause — none required the "leave unchanged, document why" fallback the mission explicitly allowed for. Re-investigating "why can't the Commander select the discovered Hornet nose turret" surfaced a second, previously-unnoticed bug (generic-sweep cross-ship contamination on a `Gimbal Mount`-typed port, the same shape as the Eclipse rack bug from SW-013C.2D) that was masking the real, confirmed swap group even on ships that DO have the port. Fixing it, plus a small canonical-label ordering fix, resolved the Warlock's "duplicate-looking" EMP entries too — both objectives shared one root mechanism.

## Objective 1 — Hornet Mk II Nose Turret Presentation (Fixed, Generically)

Re-investigation found **two** real, independent, non-Hornet-specific bugs stacking on top of SW-013C.2E's own correct discovery:

1. **Missing catalog entry.** `ANVL_Hornet_F7C_Mk2_Nose_Turret` (the confirmed swap-group alternate) was never referenced as any raw-data ship's own factory default, so it never reached the shipped runtime component catalog — the same shape of gap SW-013C.2B's report already documented for `UMNT_ANVL_S5_Rotodome_Mk2`, and SW-013C.2E's own fix for the Retaliator's module variants. Fixed by adding it to the same `CONFIRMED_SUPPLEMENTARY_ENTITY_CLASSES` list `scripts/generateComponentCatalog.ts` already carries.
2. **Generic-sweep cross-ship contamination.** Confirmed live: even with the catalog gap fixed, the F7CM Mk2's own "Nose Weapon Mount" (a real, factory-occupied `Gimbal Mount`-typed port) offered a dozen unrelated real ships' own turrets (Anvil Arrow, Lightning F8C, Anvil Terrapin, Consolidated Outland Mustang, Origin Jumpworks 85X, Tumbril Storm) — all "matching" purely because DataCore's `Turret` category translates generically to `Gimbal Mount`, the exact same string this port's own type already is, so the generic sweep could only ever match by size. This is the identical root cause SW-013C.2D found and fixed for the Eclipse's missile rack (`Missile Rack` type vs. category collision) — extended here to `Gimbal Mount`, using the exact same "swap-group-only when a confirmed group exists, generic sweep otherwise" mechanism. Verified across the whole fleet (144 Turret-category ports with confirmed groups exist catalog-wide) that this narrowing never fires unless a real confirmed group exists for that specific port — full regression suite stayed green.

**The Ghost itself is unaffected by either fix** — it still does not import `hardpoint_weapon_nose` at all (confirmed unchanged by `hornetNoseTurretDiscovery.test.ts`, carried over verbatim from SW-013C.2E). Per this objective's own explicit instruction, that remains undocumented-as-a-limitation, not fabricated: ADR-014 gained a new amendment section explaining precisely why (see Files Changed).

## Objective 2 — Warlock EMP Presentation (Fixed)

The "duplicate-looking Factory Device" ambiguity was a **label-ordering bug**, not a compatibility or policy question — REP-VS remains genuinely, authoritatively compatible (SW-013C.2E's own finding stands, re-confirmed). Root cause: `newTargetOptionsFor` pinned Current/Factory/Installed **before** running the swap-group sweep, so whichever of those three values happened to already be a swap-group member (REP-8, the factory default) got added first, with no label — and the swap-group sweep's own later pass, upon reaching that same value, saw it already present and skipped it, leaving it permanently unlabeled while REP-VS (reached only via the sweep) got the full canonical label. Fixed by reordering: the swap-group sweep now runs **first** for every swap-group-only port type, so Current/Factory/Installed pinning becomes a pure fallback for values that AREN'T swap-group members (preserving that behavior unchanged for non-member/legacy values). Both REP-8 and REP-VS now read `"{name} — EMP, S4"` — visibly parallel, clearly two real, comparable, differently-named devices of the identical class, not an ambiguous duplicate.

## Objective 3 — Retaliator Commander Messaging (Implemented)

A new, narrow, evidence-gated `DORMANT_TOPOLOGY_ENTITY_CLASSES` set (currently the two confirmed Ordnance module variants) drives a small "Additional Topology Pending" badge next to the Front/Rear Module row, shown only once the Commander's current target resolves to one of those two entities. The badge's own tooltip reads: *"This module contains additional topology (its own torpedo/bomb mount) that will be supported by a future topology engine. Not a failure — the module selection itself is fully saved."* No speculative child port, no placeholder graphic — confirmed via a dedicated test that no fabricated child row (`hardpoint_torpedo_launcher_*`, "Torpedo Rack") ever appears.

## Objective 4 — Commander Label Cleanup, Phase 1 (Implemented)

A small, generic `stripRedundantShipNamePrefix(displayName, shipName)` helper drops a leading `"{Ship Name} "` prefix from swap-group option **labels only** — never the committed value, which remains the real, full catalog display name (verified by a dedicated test asserting the saved `targetItem`/`targetEntityClass` are unchanged). "Retaliator Cargo Front Module" now reads "Cargo Front Module"; "Retaliator Ordnance Rear Module" reads "Ordnance Rear Module". "Front"/"Rear" is deliberately **preserved** — the work order's own illustrative "Unladen Module" example would make the Front and Rear ports read identically, which the mission's own overriding rule ("do not remove information needed for clarity") forbids. The mechanism is ship-name-generic (any future ship whose components redundantly repeat the ship's own name gets this for free); the Retaliator is simply the only current case.

## Objective 5 — Ship Workspace Density Pass, Phase 1 (Implemented)

Conservative, targeted reductions, confirmed via live screenshot to remain fully readable:
- **Row cell padding** (`<td>`, the single most-repeated element in the page — every port row, every ship): `py-2` → `py-1.5`, applied to all 17 occurrences via a scoped replace that explicitly excluded button/control padding.
- **Root section spacing**: `space-y-6` → `space-y-4` (the gap between the page header, sticky context, hero banner, loadout selector, and systems workspace panel).
- **Group header row** (the collapsible "CORE COMPONENTS"/"MISSILE RACKS"/etc. toggle buttons): `py-3` → `py-2.5`.

No table header padding, no button/control padding, and no hero banner padding were touched — those are single, prominent, non-repeated elements where the density leverage is low and the redesign risk is comparatively higher; left for the Phase 2 UX pass the Chief Architect's own remarks already scope for after topology freeze.
