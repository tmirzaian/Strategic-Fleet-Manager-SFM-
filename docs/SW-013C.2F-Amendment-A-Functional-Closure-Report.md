## Summary

This Amendment exists because SW-013C.2F's own "Commander-Readiness Statement" was premature: discovery and presentation were ahead of execution — the picker could show a real, catalog-known component that compatibility, topology, or persistence still disagreed with. All four findings trace back to a small number of root causes, none of them where the original Commander report guessed:

- **Finding 1** was never a validator, parent-identity, or reconciliation defect — it was a UI-layer fan-out bug that predates this mission.
- **Finding 2** was never fixable by tightening the size/category sweep further — the missing signal was a real DataCore field (`AttachDef.RequiredTags`) this codebase had never read before.
- **Finding 3** was never a generator or parser defect — it was a single stale hand-authored override, written before the entityClass-first resolution architecture existed, silently masking four other real components.
- **Finding 4** is not fixable at all within this Amendment's scope — direct evidence shows the Ghost's own nose position is a structurally different, real hardpoint, not an empty one, and materializing it would require crossing an architectural invariant (every Port is derived from that ship's own real data) that deserves independent design review, not a fast-follow fix.

## Finding 1 — Eclipse Bomb Rack Save Failure (Fixed)

**Root cause:** `withMissileRackAggregation` synthesizes one summarized aggregate row per rack with a synthetic `slotLabel` (e.g. `"Torpedorack — Bomb"`) that has no real corresponding Hardpoint. `MissionComposer.tsx` already fans a Commander's aggregate-row selection out to every real per-child `slotLabel` (`childSlotLabels`, established EWO-054) before writing it to its own local edit state — `ShipWorkspacePrototype.tsx`'s own `commitNewTarget` never received the equivalent fix when its aggregate-row rendering was built. It wrote the Commander's bomb selection directly to the synthetic `slotLabel`, producing a `targetOverrides` entry `saveMissionConfiguration` could never resolve — reproducing the exact reported error, `"Could not save — 1 assignment(s) referenced a port that no longer exists on this ship: Torpedorack — Bomb"`. Confirmed the entire transaction (including the rack's own pending parent-target swap) rolled back together, matching the report.

**Fix:** `commitNewTarget` now fans out to `hp.missileAggregate?.childSlotLabels ?? [hp.slotLabel]`, mirroring `MissionComposer.tsx`'s own established pattern exactly.

**Verification:** permanent regression test (`src/pages/__tests__/sw013c2fAmendmentAFinding1.test.tsx`) covers the Amendment's own required matrix — all three real Eclipse bomb rack alternates (1×S10, 4×S5, 20×S3) — each: select via the real UI picker, assign the correct-size bomb to every synthesized slot via the aggregate row's own picker, save via the real "Save Changes" button (asserting no "Could not save" banner), then a genuine store reload (`vi.resetModules()`, not a same-module re-import) confirming the parent rack AND every child bomb payload survive with correct identity, count, and size. Live Playwright proof: 20×S3 rack + Thunderball Bomb assignment saved with zero errors and survived a real full-page browser reload.

## Finding 2 — Missile Rack Compatibility Too Broad (Fixed)

**Root cause:** the Warlock's own rack ports carry no confirmed swap group, so the generic size/category sweep was the only signal available — and it had no way to know a same-size, same-category candidate could still be authoritatively bound to another vessel. Direct `dcb query` inspection of the raw DataCore record found the real, authoritative, non-name-based signal this codebase had never read: `AttachDef.RequiredTags`. The leaking candidate, `MRCK_S03_GAMA_Railen_Dual_S02` ("Gatac Missile Rack 2xS2"), carries `Tags: "flightReady $gama_railen"` + `RequiredTags: "gama_railen"` — CIG's own self-referential vessel-lock convention (the identical `$`-prefixed tag convention this codebase's own swap-group discovery engine already uses for confirmed-group fallback naming). The Warlock's own factory rack carries no `RequiredTags` at all.

**A necessary refinement, found via the full regression suite:** `RequiredTags` alone is not a vessel-binding signal — it is also used for ordinary, widely-shared port-family requirements (e.g. every real mining laser carries `RequiredTags: "miningMount"`, shared across dozens of unrelated ships; excluding on that alone broke 6 real, unrelated tests on the first pass). The correct, narrower signal — confirmed against the raw data for both cases — is that the required tag is vessel-binding **only** when the same entity's own `Tags` field also carries it with a `"$"` prefix (a genuine self-reference), never a bare shared requirement.

**Precedence now implemented, matching the Chief Architect's own ruling exactly:** Certified swap group (unchanged, checked first) → generic size/category sweep, **now excluding any candidate whose `vesselBoundTags` is non-empty** from the generic fallback only (never from save-time validation, never from a confirmed swap-group hit, which already tag-matched it at discovery time).

**A second, necessary refinement:** `compatibilityShapeKey` (the mechanism that decides whether two same-named candidates are "compatibility-equivalent" and safely collapsible) did not previously account for vessel-binding. A same-named pair split only by vessel-binding (e.g. "Vanduul S3 Quad Missile Rack," one open, one hull-locked to the Vanduul Blade) would otherwise silently collapse to whichever entityClass happened to sort first — capable of hiding the genuinely open one behind a vessel-bound one. Extended to treat open/restricted as distinct shapes, so both now surface as separate, correctly-labeled options exactly like any other genuinely ambiguous name.

**The Fury/Ghost tension, resolved:** initial investigation found the SW-008C regression test's own example (a Fury rack on the Hornet Ghost) was structurally identical to the Warlock leak (another ship's own factory rack). Direct `dcb query` inspection resolved this cleanly: the Fury's own rack **also** carries a self-referential vessel lock (`Tags: "... $MISC_Fury_Miru"` + `RequiredTags: "MISC_Fury_Miru"`) — it was never a certified legitimate cross-ship swap, only a permissive sweep result that had not yet been caught. SW-008C's test now swaps to a genuinely unrestricted, real rack (`MSD-322`/`MRCK_S03_BEHR_Dual_S02`) instead, preserving its own stated intent (verify immediate child-topology regeneration on a real swap).

**Verification:** `src/pages/__tests__/sw013c2fAmendmentAFinding2.test.tsx` (5 tests) — Warlock exclusion, Warlock's own rack still offered, the Vanduul ambiguity-splitting mechanism, catalog-level `vesselBoundTags` assertions for both racks. Live Playwright proof: Warlock's Left Missile Rack picker offers exactly `Intentional Empty`, `MSD-322`, `MSD-313` (see Finding 3), and `MSD-341` — no Gatac, no Railen.

## Finding 3 — MSD-313 Rack Geometry / Child Count Incorrect (Fixed)

**Root cause:** `src/data/componentCatalog.ts`'s hand-authored `CATALOG` override table carried `'MSD-313 Missile Rack': { category: 'Missile Rack', size: 3 }` (EWO-023), added before this codebase's entityClass-first, ambiguity-aware resolution chain (EWO-STAB-004A/CAT-003) existed, to patch the older "first entry wins" name-only dedup bug. This override unconditionally wins over entityClass-based resolution, **regardless of which real entityClass is actually being asked about**. Direct catalog audit found "MSD-313 Missile Rack" is now shared by **five** real, differently-shaped entityClasses: the Gladius's own genuine `MRCK_S03_BEHR_Single_S03` (MissileLauncher/S3, 1 real S3 child — exactly the Commander's own expected "1×Size 3 missile"), plus four unrelated real `BombLauncher` racks on the Spirit A1/Starlancer at sizes 3/5/10. The override was forcing every one of them to the same wrong answer — the exact "label says one thing, geometry subtitle says another, wrong child count" symptom reported, confirmed live before the fix (label "— Bomb Launcher, S10" alongside a geometry subtitle reading "S3 · 1 × S3 Missiles").

**Fix:** the stale override removed. Every real compatibility/save/readiness caller in this codebase already supplies `itemEntityClass` (confirmed by `shipDefinitions.test.ts`'s own fleet-wide factory-loadout validation, which passed with zero new exceptions needed) — removing the override lets each ship's own real installed entity resolve correctly. A caller with no entityClass now correctly reports `ambiguous` for this name instead of silently guessing the Gladius's own shape for an unrelated Spirit/Starlancer bomb rack.

**Live-verified result:** the Warlock's own missile rack picker (an unrelated ship, generic sweep) now shows `"MSD-313 Missile Rack — Missile Rack, S3"` with a correctly-matching `"S3 · 1 × S3 Missiles"` subtitle — label and geometry agree, and the four unrelated BombLauncher variants correctly fail this Missile-Rack-typed port's compatibility check rather than being silently offered.

**Verification:** `src/store/__tests__/sw013c2fAmendmentAFinding3.test.ts` (3 tests) — the required live-swap proof (old topology removed → MSD-313 selected → exactly one S3 missile child created) plus a genuine-reload regression, plus catalog-level ambiguity/resolution assertions. `src/pages/__tests__/ShipWorkspacePrototype.test.tsx`'s own SW-008C test now uses MSD-313 as its swap target, doubling as a second independent live confirmation (factory 4×S1 → MSD-313's real 1×S3, no stale slots).

## Finding 4 — Hornet Mk II Nose Turret (Investigated, Closed as a Documented Limitation)

Per the Chief Architect's own explicit instruction, Engineering was directed to do one of two things: implement the capability generically and safely if genuinely bounded, or stop and provide a scoped architecture proposal. Direct re-inspection of every currently-imported Hornet Mk II variant's own real port data found the gap is **stronger** than "factory-empty" — the Ghost's own nose position is not the turret port (`hardpoint_weapon_nose`) sitting unoccupied; it is a **different, real, physically-present port** (`hardpoint_nose_cone`) under a different internal name, a different DataCore port classification (`Module` vs `WeaponTurret`), a different equipment group, a different size (S1 vs S3), owning none of the turret variant's own two real child weapon mounts. There is no row to unhide — materializing it would mean grafting another ship's own hardpoint subtree onto this one by analogy, the first case of its kind in this codebase, crossing the invariant that every `Port` is derived only from that specific ship's own real data.

This is not "genuinely bounded" in the sense the Amendment asked Engineering to check for before implementing. **Engineering elected the second option: the Nose Turret is explicitly, honestly documented as unsupported in the current Beta — no synthetic port, no Hornet-specific special case.** Full evidence, two rejected implementation shapes, and the recommendation are recorded in the new `docs/DormantHardpointMaterializationProposal.md`, cross-referenced from `docs/ADR/ADR-014-Configurable-Slot-Architecture.md`'s own existing amendment on this same gap. No code change was needed or made — the Ghost's own real Nose Cone port already presents correctly (confirmed live: its own real confirmed swap-group alternatives, no misleading turret implication).
