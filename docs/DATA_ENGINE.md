# SFM Data Engine — Architecture

This document describes the foundation for the Data Engine that will
eventually replace Strategic Fleet Manager's handcrafted seed data
(`src/data/seed.ts`) with imported Star Citizen game data. **No importer
exists yet.** This is the architecture future importer code will plug into.

## Three data layers

### Layer 1 — Raw CIG Data (`/raw-data`)

Unmodified StarBreaker exports. Never edited by hand or by any tool in this
repo. Example filenames (illustrative — no real files are checked in yet):

```
/raw-data
    Ghost.json
    Corsair.json
    MOLE.json
    Mount_Gimbal_S3.json
```

### Layer 2 — Normalized Game Data (`/generated-data`)

Generated automatically from Layer 1 by a future Normalizer + Writer.
Human-editable game data does not belong here — everything in this folder
is regenerated output, not source of truth.

```
/generated-data
    ships.json
    ports.json
    components.json
    factory-loadouts.json
    compatibility.json
    display-name-map.json
```

### Layer 3 — Player Data

Everything user-specific: Installed Loadouts, Target Builds, Hangar
Inventory, Captain's Log, Fleet Priorities, Roadmap. This layer is not
regenerated by the Normalizer and is not part of `/generated-data` — it's
the only layer today's app (via `src/data/seed.ts` and
`src/store/useFleetStore.ts`) actually populates with real data, since
Layers 1 and 2 don't have an importer yet.

**Seed data is not player data.** `src/data/seed.ts` is demo/sample
content — its ships, builds, and hardpoints are reconstructed fresh on
every load and are never themselves written to `localStorage`. What *is*
real player data is whether the user has removed, renamed, or re-owned
one of those seed ships — persisted as a small diff
(`seedAssetOverrides`) rather than by replaying seed content through the
same pipeline as imported/manual ships. A player's fleet legitimately
being empty (every ship removed) is a valid, persisted Layer-3 state, not
evidence of missing storage — see
`docs/ADR/ADR-004-Fleet-Ownership-Sync-Authority.md` and
`docs/Architecture.md`'s "Fleet ownership and persistence" section.

## Where the code lives

```
src/
  engine/
    types/          Ship, Port, Component, CompatibilityRule,
                     FactoryLoadout, InstalledLoadout, TargetBuild,
                     EquipmentGroup, DisplayNameMap
    compatibility/   isCompatible(), getCompatibleComponents(),
                     validateLoadout(), flattenPorts() — pure logic, no UI
    displayNames/    resolveDisplayName() and DisplayNameMap types
    importer/        Importer / Validator / Writer interfaces + the
                     DataEnginePipeline contract — NOT implemented
  normalizer/
    interfaces.ts    Normalizer interface — NOT implemented
  generated/
    index.ts         Typed, empty placeholders for what a future Writer
                     will eventually populate from /generated-data
```

`src/engine/types` is intentionally separate from the existing
`src/types/index.ts` used by the React app (Mission Control, Fleet
Dashboard, Ship Detail, etc.). They represent different layers and are not
merged or aliased — see the note at the top of `src/engine/types/ship.ts`.
Nothing in the current UI imports from `src/engine`, `src/normalizer`, or
`src/generated` yet.

## The Port model

`Port` (`src/engine/types/port.ts`) is the heart of the data model. Every
mount point on a ship — a hardpoint, a turret, an internal bay — is a Port.
Ports are recursive (`children: Port[]`) so nested CIG port structures
(e.g. a turret with its own weapon mounts) don't have to be flattened away
during normalization. Each Port carries three separate item references:

- `factoryItemId` — CIG's stock component for this slot (immutable,
  belongs to the ship's `FactoryLoadout`).
- `installedItemId` — what the player currently has installed
  (`InstalledLoadout`, Layer 3).
- `targetItemId` — what the player wants installed for a given
  `TargetBuild` (Layer 3).

This three-way split is what lets the existing UI-level hardpoint status
logic (`src/utils/hardpointStatus.ts`) distinguish "never touched" (Missing)
from "touched but not yet the right thing" (Upgrade Available) — the same
rule set this data model is designed to eventually back.

## Display names

Internal identifiers (e.g. `hardpoint_gun_left_wing`) must never reach the
UI. `resolveDisplayName()` (`src/engine/displayNames/resolveDisplayName.ts`)
looks an internalName up in a `DisplayNameMap` and falls back to a crude
humanized version of the internalName itself if no mapping exists yet —
so an unmapped name degrades gracefully instead of leaking raw CIG
identifiers into the interface.

## Compatibility engine

Pure, UI-free functions in `src/engine/compatibility/`:

- **`isCompatible(component, rule)`** — does a Component satisfy a
  `CompatibilityRule` (or a `Port`, which is structurally a superset of
  one)? Checks `category` against `allowedTypes`, `subtype` against
  `allowedSubtypes`, and that `size` falls within `[minSize, maxSize]`. An
  empty allow-list on either axis means "unconstrained", not "nothing
  allowed".
- **`getCompatibleComponents(rule, components)`** — filters a Component
  list down to everything compatible with a given rule/Port.
- **`validateLoadout(loadout, ports, components)`** — checks every
  assignment in an `InstalledLoadout` against its Port's rules and returns
  a `LoadoutValidationResult[]` (`ok` / `empty` / `incompatible` /
  `invalid`). This is a data-integrity check — "is this component legally
  allowed here" — and is intentionally separate from
  `hardpointStatus.ts`'s "does Installed match Target" question.
- **`flattenPorts(ports)`** — depth-first flatten of a recursive Port tree,
  used internally by `validateLoadout` and available for any future
  consumer that needs a flat lookup.

These are implemented now, unlike the importer, because they're pure
logic over already-defined types with no dependency on real StarBreaker
data.

## The importer pipeline (interfaces only — not implemented)

```
Importer → Normalizer → Validator → Writer
(raw-data)  (in memory)  (in memory)  (generated-data)
```

- **`Importer`** (`src/engine/importer/interfaces.ts`) — Layer 1 access
  only. `listSources()` + `read(path)`, returning opaque `RawRecord`
  (`unknown`) values. Never normalizes, validates, or writes.
- **`Normalizer`** (`src/normalizer/interfaces.ts`) — turns `RawRecord[]`
  into a `NormalizedGameData` bundle (ships, ports, components,
  factoryLoadouts, displayNameMap).
- **`Validator`** — checks a `NormalizedGameData` set for internal
  consistency (e.g. every `Port.shipId` resolves to a real `Ship`) and
  returns `ValidationIssue[]`. Distinct from `validateLoadout()`, which
  validates a *player's* loadout, not the game data itself.
- **`Writer`** — the only stage allowed to touch `/generated-data`;
  persists a validated `NormalizedGameData` set to disk.

`DataEnginePipeline` (`src/engine/importer/pipeline.ts`) ties the four
stages together as a single type, documenting the intended flow without
providing a runnable implementation. Building a concrete importer,
normalizer, validator, and writer — and actually parsing StarBreaker
JSON — is future work, out of scope for this sprint.

## Non-goals for this sprint

- No StarBreaker JSON parsing.
- No importer implementation.
- No wiring into `src/pages`, `src/components`, or `src/store` — the
  existing app continues to run entirely on `src/data/seed.ts` and
  `src/store/useFleetStore.ts` until a real importer exists.

## Addendum: the generalized StarBreaker import pipeline

A later sprint replaced the Gladius-only proof-of-concept (`GladiusImporter`
/ `GladiusNormalizer`) with a reusable, data-driven pipeline. Nothing
below is ship-specific — the same code processes any raw-data file that
matches the tolerant `RawShipExport` shape.

```
raw-data/*.json
      ↓
StarBreakerImporter        (src/engine/importer/starBreakerImporter.ts)
      ↓  RawRecord (unknown, unparsed)
ShipNormalizer              (src/normalizer/shipNormalizer.ts)
  ├─ loadoutNodeAdapter.ts    adaptLoadoutNodes() — legacy/StarBreaker
  │                           node schemas -> one CanonicalLoadoutNode shape
  ├─ componentMetadataResolver.ts + componentMetadataEnrichment.ts
  │                           (Mission M-008) — exact-key lookup into the
  │                           locally-generated Component Metadata Catalog;
  │                           fills factoryComponent fields the adapter
  │                           couldn't supply, never overwriting verified
  │                           (legacy) data
  ├─ classificationTranslator.ts + classificationEnrichment.ts
  │                           (Mission M-009) — the ONLY place DataCore's
  │                           Type/SubType taxonomy is interpreted into a
  │                           canonical node.portType classifyPort() already
  │                           understands; never overwrites a legacy portType
  ├─ portClassifier.ts        classifyPort() — the one place that decides
  │                           include/exclude and EquipmentGroup, from
  │                           node.portType regardless of which stage set it
  ├─ displayNameGenerator.ts  generateDisplayName() — internal name →
  │                           player-friendly name + positionLabel
  ├─ portConstraintBuilder.ts real allowedTypes/allowedSubtypes/min/maxSize,
  │                           or null + a warning — never invented
  ├─ factoryLoadoutBuilder.ts real factory components, or an explicit
  │                           empty assignment — never "Factory Component"
  └─ equipmentRelationship.ts + equipmentResolver.ts
                              (Mission M-010) — collapses a mount/rack
                              container port (WeaponTurret, GimbalMount,
                              Turret, MissileRack) to its leaf item(s), but
                              keeps independent equipment (QuantumDrive,
                              JumpDrive, ...) as its own separate,
                              never-collapsed assignment — decided from
                              Port.canonicalPortType alone, never a name
      ↓  NormalizedShipPackage
validateNormalizedPackage() (src/normalizer/validation.ts)
      ↓  same package, warnings/errors merged in
GeneratedDataWriter          (scripts/generatedDataWriter.ts, Node-only)
      ↓
generated-data/*.json
      ↓  (Vite JSON import, browser-safe, no pipeline execution in-browser)
src/generated/importedShips.ts
      ↓
Ship Detail's "(Imported)" developer option
```

### Running it

```bash
npm run import:ships                                    # every raw-data/*.json
npm run import:ship -- "raw-data/AEGS Gladius.json"      # one file
```

Runs entirely under Node (`scripts/importShips.ts`, via `tsx`) — the React
dev server is never required. It prints a summary (ships imported, ports
included, components discovered, assignments created, warnings, errors)
and writes `generated-data/ships.json`, `ports.json`, `components.json`,
`factory-loadouts.json`, `installed-loadouts.json`, `target-builds.json`,
`display-name-map.json`, and `import-report.json` — one combined file per
record type across every imported ship, never touching player data.

### Why the browser no longer runs the pipeline live

The original Gladius proof-of-concept ran `GladiusImporter` and
`GladiusNormalizer` in the browser at module load, via a Vite JSON import
of the raw-data file. The generalized pipeline instead treats import as an
offline step: `npm run import:ships` produces `generated-data/*.json`,
and `src/generated/importedShips.ts` reads that back with a plain Vite
JSON import — no `StarBreakerImporter`/`ShipNormalizer` code ships to the
browser bundle at all. This is what "the importer runs independently from
React" means in practice.

### Component Catalog Generator (Mission M-007)

A separate, standalone offline tool — not part of the `ShipNormalizer`
pipeline above, and not yet consumed by it:

```
raw-data/*.json
      ↓ (scripts/componentCatalog/rawEntityCollector.ts — independent of src/normalizer)
distinct entity classes actually mounted by SFM's ship exports
      ↓ (scripts/componentCatalog/dcbQuery.ts)
starbreaker.exe dcb query EntityClassDefinition --filter "EntityClassDefinition.<exact>"
      ↓
generated-data/component-metadata-catalog.json
```

Run via `npm run generate:component-catalog`. Requires a local install of
both the [StarBreaker](https://github.com/diogotr7/StarBreaker) toolkit
and Star Citizen itself (LIVE channel; `Data.p4k` read directly, never
fully extracted) — this is a developer-machine tool, not something CI or
the app runs.

**Purpose:** produce the authoritative, exact-entity-class-keyed metadata
(`category`/`subtype`/`size`/`grade`/`manufacturerRef`/`localizationKey`)
that a future `ComponentMetadataResolver` (ADR-003, still "Proposed") will
need — StarBreaker ship exports name entity classes but carry none of
this metadata themselves.

**Key policy:** exact full-record-name match only
(`EntityClassDefinition.<entityClass>`). Bare substring/glob filters
return unrelated collisions (confirmed during investigation — e.g.
`Mount_Gimbal_S3` substring-matches 12 unrelated records across other
ships) and are never used.

**Local-only, no redistribution decision:** the generated catalog is
gitignored and stays on the generating developer's machine. Committing
derived DataCore data to the repository — or redistributing it at all —
is an **open licensing question that has not been decided** (see
ADR-003). Treat every catalog as personal, disposable build output, the
same as any other `/generated-data` artifact, regenerable at any time
from a licensed local game install.

**Build/version tracking:** every catalog embeds the exact game
`branch`/`version`/`p4ChangeNum` it was built from (read live from the
install's `build_manifest.id`, never hard-coded) plus the StarBreaker
tool version and a generation timestamp, so a catalog can never be
mistaken for one built against a different patch.

**Channel support:** LIVE only. PTU/EPTU are explicitly out of scope for
the normal workflow.

**Isolation guarantees:** the generator does not import from
`src/normalizer`, does not write or modify any `generated-data/*.json`
file other than `component-metadata-catalog.json`, and does not mutate
`raw-data/`.

### Component Metadata Resolver, Classification Translation, Equipment Resolution (Missions M-008/M-009/M-010)

`src/normalizer/componentMetadataResolver.ts` reads the catalog above
(lazily, once, cached); `src/normalizer/classificationTranslator.ts`
interprets its DataCore `Type`/`SubType` taxonomy into the canonical port
types `portClassifier.ts` already recognizes; `src/normalizer/equipmentRelationship.ts`
+ the refactored `src/normalizer/equipmentResolver.ts` decide, from that
same canonical port type, whether a port-with-children is a mount/rack
container (collapse to its leaf item) or independently real equipment
(never collapsed) — see docs/ImportPipeline.md's "Stage 4"/"Stage
4b"/"Stage 4c" for the full pipeline placement, field-precedence rules,
translation table, `Mount_Gimbal_S3` decision, and the Quantum
Drive/Jump Drive fix. As of Mission M-010 the real Gladius fixture
produces 26 classified ports across 9 equipment groups with zero
validation errors, correctly resolving both the Quantum Drive (Beacon)
and its nested Jump Drive (Explorer) as separate equipment, and the
golden fixture (`goldenFixture.ts`) has been reconciled against this
authoritative result (14/14, zero failures) — the "Nothing in `src/`
reads the catalog" and "ADR-003, still Proposed" statements from earlier
missions are superseded by this; ADR-003 itself remains "Proposed" only
because the catalog's licensing/redistribution question is still
unresolved, not because the resolver is unbuilt.

### Test fixtures

`raw-data/AEGS Gladius.json` and `raw-data/AEGS Avenger Titan.json` are
both **real** StarBreaker `entity export --dump-hierarchy` exports from
the frozen LIVE 4.8.184.64329 install (Mission M-011A restored the
Avenger Titan fixture, which had been missing since the schema
migration — see docs/ImportPipeline.md's "Certification fixtures"
section for the exact export command and provenance). Neither is
hand-authored or synthetic. Both exercise recursive weapon-mount and
missile-rack hierarchies and include plenty of irrelevant nodes (doors,
seats, controllers, thrusters, mesh helpers) that exercise
`classifyPort()`'s exclusion logic naturally, since that's what a real
ship export actually contains.

**Synthetic scenarios are covered separately, not forced into these real
fixtures:** missing-constraint handling, cargo-port classification, and
specific exclusion examples are tested with dedicated hand-built
fixtures in `src/normalizer/__tests__/shipNormalizer.test.ts` and
`validation.test.ts` — see Mission M-011A's report for why forcing such
scenarios into a real ship export would misrepresent it.

See `src/normalizer/__tests__/` for the unit and integration test suite
(`npm run test`).
