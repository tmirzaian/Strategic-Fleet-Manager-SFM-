# SW-013C.2B — Module Taxonomy Activation: Implementation Report

Operation: Swamp Fox · Classification: Architecture Activation · Priority: Critical Commander Validation Blocker

**Status: Implemented, tested, live-validated. Not committed — awaiting Chief Architect review and Commander visual certification.**

## Summary

Activated the previously-designed Module taxonomy (`docs/ADR/ADR-014-Configurable-Slot-Architecture.md` Decision D5, `docs/ModuleTaxonomyProposal.md`) so the Hornet Ghost Mk II's Nose and Center mounts, and the Retaliator's Front and Rear module bays, render truthfully in Ship Management — real factory components, real Configurable Slot compatibility, real readiness participation, zero fabrication. This is a classification fix, not a topology-generation change: every affected port was already present in the raw StarBreaker export with a real factory-installed entity; it was excluded only because its DataCore category (`Module`, or `Misc` for the Hornet's nose position) had no translation rule.

**`src/normalizer/classificationTranslator.ts`** — two new, individually-verified entity-class allowlists, never a blanket category match:

- `CONFIRMED_MODULE_ENTITY_CLASSES` (DataCore category `Module`): `UMNT_ANVL_S5_Cap`, `UMNT_ANVL_S5_Cap_Mk2`, `UMNT_ANVL_S5_Rotodome`, `UMNT_ANVL_S5_Rotodome_Mk2`, `AEGS_Retaliator_Module_Front_Base`, `AEGS_Retaliator_Module_Rear_Base` — each individually confirmed via direct catalog inspection to be a real, swap-group-verified ship equipment position, out of exactly 13 total `Module`-category entities in the full catalog. The 7 not listed (`GLSN_Basher_Addon_Mohawk_Default` — a ground-vehicle cosmetic bodykit; `RSI_Apollo_Module_*` ×4; `ANVL_Hornet_F7C_Cargo_Mod`/`_Mk2_Cargo_Door`) remain unclassified, exactly as before this mission — real, unverified Module-category data, deliberately excluded per Objective 1's own instruction.
- `CONFIRMED_NOSE_CAP_ENTITY_CLASSES` (DataCore category `Misc`): `ANVL_F7_Mk2_NoseCap`, `ANVL_F7CR_Mk2_NoseCap` — exactly two entities, not a blanket Misc translation.
- The `TranslationRule` matching logic was extended with an optional `entityClassAllowlist`, checked in `translateClassification`'s rule lookup. (First implementation attempt omitted this check from the actual `find()` predicate — caught immediately by the pre-existing regression suite; see Errors/Fixes below.)

**`src/normalizer/portClassifier.ts`** — `Module: 'Modules'` added to `INCLUDED_TYPE_TO_GROUP`.

**`src/engine/types/equipmentGroup.ts`** — new `'Modules'` `EquipmentGroup` value, not folded into `Utility` (per `ModuleTaxonomyProposal.md`'s own "Why not Utility" finding: same-category Module items are not broadly interchangeable, unlike Utility's real family).

**`src/data/shipDefinitions.ts`** — `compatibilityTypeFor`'s `equipmentGroup` switch gained a `'Modules' -> 'Module'` case (singular, matching every other compatibility-type string's convention), and `topLevelGroupLabel` gained `'Modules' -> 'Modules'` for the Commander-facing taxonomy section.

**`src/utils/commanderSystemTaxonomy.ts`** — `TOP_LEVEL_GROUP_ORDER` gained `'Modules'`, placed after Pilot Weapons (a Module position's confirmed alternatives include real armament).

Unknown data stays safely excluded by construction: any DataCore category outside these two exact allowlist checks (or an allowlisted category with an entity class not on the list) falls through to the pre-existing `unresolved` path, unchanged.

## Objective 3 — Swap-Group-Only Compatibility

**Two coordinated changes, both minimal:**

1. **`src/data/componentCatalog.ts`** — `checkCompatibility` gained one early return: `if (portType === 'Module') return true`. This is the negative-space half of the certified-only rule — a Module port's already-set target is never flagged a false "Invalid Target" by the generic size/category sweep, even when the candidate independently resolves via some unrelated recognized category (the Ball Turret alternative resolves as DataCore category `Turret` elsewhere in the app — the generic sweep would otherwise translate that to `'Gimbal Mount'` and flag a legitimate certified target invalid). `Module` was deliberately **not** added to `CATEGORY_TO_PORT_TYPE` — that omission is what makes the generic *suggestion* sweep naturally offer nothing for a Module port, satisfying "never by category alone" without a second gate.
2. **`src/pages/ShipWorkspacePrototype.tsx`** — `newTargetOptionsFor` gained a Module-specific branch: for `hp.type === 'Module'`, skip the generic full-catalog sweep entirely and instead resolve the port's real swap-group `eligibleComponents` (via `configurableSlotFor`/`resolveComponentByEntityClass`), pinning each successfully-resolved alternative as an option.
3. **`scripts/configurableSlots/catalogRuntimeSchema.ts`/`catalogRuntimeWriter.ts`** — the runtime catalog's own `ConfigurableSlotRuntimeRecord` gained `eligibleComponents?: string[]` (schema v1 → v2), the real member entity-class list, alongside the pre-existing `eligibleComponentCount`. SW-011A's own Phase I was deliberately read-only (count-only, "not a picker"); this mission activates real operational selection, which needs the actual list. `src/generated/configurableSlots.ts` (the browser loader) mirrors the same optional field.

**Validated live** (Hornet Mk II): 7 eligible components resolved for the Center swap group; the Ball Turret alternative is genuinely offered in the New Target picker and can be selected and saved.

## Objective 4 — Readiness Policy

**No Module-specific readiness code was written**, per the work order's explicit instruction. The Chief-Architect-approved hybrid model (neutral while following factory default, readiness-bearing once a real alternative is targeted, Factory-Cap-Targeted reads Ready, Intentional Empty uses the pre-existing shared `'—'` mechanism) is delivered entirely by the existing, unmodified `computeHardpointStatus`/`calculateBuildProgress` engine:

- A Module port's default state (installed = target = factory Cap) already produces `status: 'OK'`, already excluded from readiness reduction — the exact same rule every port type has always used.
- Once a Commander targets a real alternative without installing it, the existing rule (`installed === factory && target !== factory` → `'Missing'`) applies unchanged, making the port genuinely readiness-bearing.
- `'—'` (Intentional Empty) already excludes a port from the `required` set in `calculateBuildProgress` — reused verbatim.

Live-verified: Ghost's readiness moved from 92% to 93% purely from the two new Module ports joining the denominator already-matched (no readiness regression); targeting the Ball Turret without installing it correctly produced `status: 'Missing'` and appeared in `progress.missingAssignments`.

## Errors Found and Fixed During Implementation

1. **Entity-class allowlist not actually enforced.** The first implementation added `entityClassAllowlist` to the `TranslationRule` type and populated it, but never checked it in the rule-matching `find()` predicate — every `Module`/`Misc` entity matched, not just the verified ones. Caught immediately by the pre-existing regression suite (a Basher cosmetic bodykit test and an unrelated "name pattern" test both failed) before this reached generated data or the UI. Fixed by adding the allowlist check to the match predicate; re-verified with a dedicated unit test proving unverified entities stay unresolved.
2. **False "Invalid Target" on a legitimately-targeted swap-group alternative.** The Ball Turret independently resolves via DataCore category `Turret` (recognized elsewhere in the app for ordinary turret compatibility) — validating it against a `Module` port through the generic category sweep produced a category mismatch and a false `Invalid Target` status. Fixed with the `checkCompatibility` early-return described in Objective 3. Caught by a dedicated store-level readiness test before reaching live validation.
3. **Stale generated data during mid-fix testing.** After discovering error #1, `ports.json` had already been regenerated once from the (still-buggy) classifier, producing 8803 ports (890 more than baseline) including the unverified Basher entities. Re-ran `npm run import:ships` after the real fix; verified byte-level via a git diff against the checked-in baseline that only the 6 confirmed entity classes now appear as Module ports fleet-wide (10 total port instances across all Hornet/Retaliator variants).

## Castillo Rack Control

**Finding, sourced directly from the codebase's own generator documentation** (`scripts/generateMissileRackSlots.ts`, lines 55-58): the missile-rack child-slot generator's own data source is filtered to `category === 'MissileLauncher' && subtype === 'MissileRack'`, **deliberately excluding** the sibling `BombLauncher`/`BombRack` category (which the CST-313 "Castillo" belongs to) as "a different real component family." This means: the underlying `componentOwnedChildSlotSpec` mechanism is genuinely generic and category-agnostic (a simple entity-class-keyed lookup, no Missile-vs-Bomb branching in the code itself) — but its **data coverage** has never included any Bomb Rack, because no currently-imported ship's factory loadout carries one (confirmed: zero raw-data files reference the Castillo at all) and the generator's own sweep explicitly excludes the category regardless. Live-probed on a Ghost wing weapon mount (size/category mismatch, as expected — Castillo is S3/BombLauncher against an S4 WeaponTurret): the picker correctly offers no match and commits nothing, with zero console errors. **Where the abstraction would break down if a ship with a native Bomb Rack were imported:** the rack itself would classify correctly (`BombLauncher`/`Bomb` already exist in `src/generated/componentCatalog.ts`'s `CATEGORY_TO_PORT_TYPE`), but its payload children would not synthesize until `scripts/generateMissileRackSlots.ts`'s own category filter is deliberately widened — a data-generation scope decision, not a code defect, and out of this mission's scope to change.

## Operation Swamp Fox Impact

- **Cross-page/state impact:** contained. The classification fix lives entirely in the shared Normalizer/import pipeline (already the single authority every ship goes through) — no new topology authority, no per-ship special case. `ShipWorkspacePrototype.tsx`'s own change (swap-group-sourced options) is additive and scoped to the one `hp.type === 'Module'` branch.
- **Data ownership:** Module ports are **SOURCE-OWNED** exactly like every other port (`factoryItem`, port identity, canonical classification) — no new ownership category was needed. Target assignments on them are **COMMANDER-OWNED**, persisted through the same `saveMissionConfiguration` authority as any other port. Readiness/compatibility remain **DERIVED**. No new **OPERATIONAL/TRANSACTIONAL** record type was introduced — install/remove on a Module port (once a Commander swaps to a real alternative) would route through the identical certified installation engine every other port already uses.
- **Future RSI resynchronization:** unaffected. Port identity (`${shipId}-port-${sourcePath}`) is unchanged for every existing port and additive for the two newly-classified ones — no existing identifier was renamed or re-keyed. A future resync attaching a newly-synchronized Hornet to this same canonical topology would not duplicate or replace a Commander's existing custom Loadout, for the same reason `reconcileBuildHardpoints` already handles any other newly-appearing canonical port: additively, by the same tiered id/label matching every other port already relies on.
- **Migration/backward-compatibility risk:** none found. Verified directly (Objective 8 test): `reconcileBuildHardpoints` appends the newly-classified Module port to a build predating this fix without touching any pre-existing row. No persist-schema version bump was required for the main fleet store; the Configurable Slot runtime catalog's own schema bumped 1→2 additively (`eligibleComponents` is optional, a pre-v2 catalog degrades to "no operational compatibility data available," never a crash).

## Remaining Data Gaps

- **The Hornet nose position has no known swap-group/alternative-component data.** Classification makes it visible and honestly represented (the real NoseCap); it does not, by itself, give the Commander an alternative to install there. This requires a further live DataCore tag investigation this mission did not perform (ADR-014's own "Open investigations" already flagged this as unresolved before this mission began).
- **`UMNT_ANVL_S5_Rotodome_Mk2`** (a confirmed Center swap-group member) is absent from the shipped runtime component catalog (`component-metadata-catalog.runtime.json`) though present in the fuller generation-time catalog — it will not resolve to a selectable option in the picker until that runtime catalog's own generation coverage is widened. Not a regression from this mission; a pre-existing gap this mission's live testing happened to surface.
- **Bomb Rack (Castillo and family) payload child-slot generation** remains explicitly out of scope for the missile-rack-slot generator, per its own long-standing design decision (see Castillo Rack Control above) — not a defect, a scoping decision for a future mission if bomb-rack ships are ever imported.
- **Eclipse torpedo payload targeting** (no child slots) and **role-conversion behavior** remain open, reconnaissance-only findings for a future, dedicated Eclipse mission.
- **Apollo/Cargo/Basher Module-category entities** remain deliberately unclassified, pending individual verification, exactly as this mission's own conservative scope required.
