# SW-013C.2G — Amendment C: Evidence Addendum, Vessel Restriction Correction

**Status:** Confirmed and fixed. The Commander's SPPV validation was correct — SFM's candidate list was over-broad. Root cause and authoritative correction found via direct live DataCore query, independent of SPPV.
**Commit:** HOLD — awaiting Commander Operational Certification.

## 1. What SPPV found

For the F7C-S Hornet Ghost Mk II, SPPV showed exactly one valid nose turret: "Mk II S2 Nose Turret" — S3 mount, 2 weapon ports, S2 children. SFM was additionally offering a second candidate ("Mk II S3 Nose Turret") that SPPV does not show for this hull. Per the work order's own instruction, SPPV was used only as the trigger for this re-investigation, never as encoded runtime authority — every correction below is sourced from a live `dcb query` against DataCore, independent of SPPV.

## 2. Root cause

The Ghost's dormant Nose Weapon port resolves its candidate list from the confirmed 2-member swap group `ANVL_Hornet_Mk2` (`ANVL_Hornet_F7A_Nose_Turret` / `ANVL_Hornet_F7C_Mk2_Nose_Turret`, `generated-data/configurable-slots.runtime.json`). That group's own generator output is flagged `"category": "C-review-required"`, with a diagnostic explicitly noting a rejected, more specific 8-member tag (`ANVL_Hornet_F7A_Mk2`) on the default component — rejected only because the swap-group resolver's own tie-break picks the *smaller* of two competing tags (a deliberate, principled heuristic for a different, already-validated case — see `scripts/configurableSlots/swapGroupResolver.ts`'s own doc comment), never evaluated for whether it was the *correct* one here. That flag was exactly the review this Amendment performed.

**Direct DataCore evidence, converging on the same conclusion from three independent angles:**

1. **`AttachDef.RequiredTags` genuinely differs between the two turrets** (live `dcb query`, not the generic `Tags` field both share identically): `ANVL_Hornet_F7A_Nose_Turret` requires `ANVL_Hornet_F7A_Mk2`; `ANVL_Hornet_F7C_Mk2_Nose_Turret` requires only the broader `ANVL_Hornet_Mk2`.
2. **The `ANVL_Hornet_F7A_Mk2` tag family is exclusively military-family**: bulk `dcb query` on `AttachDef.Tags` shows it held only by `ANVL_Hornet_F7A_Mk2`, `_Exec_Military`, `_Exec_Stealth`, `_PU_AI_UEE`, `_AI_Super_Crim`, `_AI_Super_CIV`, plus the two turret components themselves — the Ghost (`ANVL_Hornet_F7CS_Mk2`) is not a member under any tag found.
3. **Factory-installation pattern**: `ANVL_Hornet_F7A_Nose_Turret` is factory-installed (`generated-data/ports.json`) only on F7A Mk2/F7CM Mk2/F7CM Mk2 Heartseeker/F7 Mk2 Collector Mod — every one a military/Super-Hornet-family variant. Never on any civilian or stealth Mk II hull.

**Weapon-child geometry correction, same investigation:** the prior "honest gap" (zero children for `ANVL_Hornet_F7C_Mk2_Nose_Turret` — no installed instance existed anywhere in the raw-data corpus to derive size from) is resolved by a genuinely different, independently authoritative DataCore source: the turret's own intrinsic component ports. A direct `dcb query` on `EntityClassDefinition.ANVL_Hornet_F7C_Mk2_Nose_Turret` shows its own `Components[].Ports[]` — two `WeaponGun` ports, both fixed `MinSize: 2, MaxSize: 2` — independent of any ship ever installing it. This directly corroborates SPPV's own "2 ports, S2" finding, sourced from DataCore, not copied from SPPV. (For comparison/completeness: the same query on `ANVL_Hornet_F7A_Nose_Turret` shows `MinSize: 2, MaxSize: 3` — a real *range*, not a fixed size, consistent with its own confirmed-installed S3 children being the practical factory value within that range.)

## 3. Fix

- **`scripts/generateTurretWeaponSlots.ts`** — added a second, explicit derivation pass (`CONFIRMED_INTRINSIC_PORT_TURRET_ENTITY_CLASSES`, `deriveFromIntrinsicPorts`) that queries a turret's own intrinsic `Components[].Ports[]` via live `dcb query` when no installed-instance evidence exists in the raw-data corpus — a genuinely different authority from the existing installed-child derivation, kept as a separate opt-in pass rather than folded together, and just as disciplined (a size *range*, `MinSize !== MaxSize`, is real and explicitly skipped rather than guessed down to one value). `ANVL_Hornet_F7C_Mk2_Nose_Turret` now resolves to `{ slotCount: 2, weaponSize: 2 }`. Regenerated `generated-data/turret-weapon-slots.json`.
- **`src/generated/dormantHardpoints.ts`** — `DormantHardpointSpec` gained `restrictCandidatesToEntityClasses?: string[]`, populated for the Ghost with `['ANVL_Hornet_F7C_Mk2_Nose_Turret']` — narrowing (never widening) the donor swap group's own full member list to only the independently-confirmed-compatible subset, with the full evidence chain cited in the module's own doc comment.
- **New field threaded end to end**, mirroring `isDormant`/`dormantDonorShipEntityClass`'s own existing pattern exactly: `Port.dormantAllowedComponentEntityClasses` / `Hardpoint.dormantAllowedComponentEntityClasses` / `FactoryHardpointTemplate.dormantAllowedComponentEntityClasses`, threaded through `materializeDormantPorts`, `importedFactoryTemplate`'s `walk()`, `materializeFleetAsset`, both branches of `fleetAssetReconciliation.ts`, `overlayCanonicalHierarchy`, and `buildCanonicalSeedCustomBuilds` (the same six sites Amendment A's own `isDormant` passthrough fix touched).
- **`src/pages/ShipWorkspacePrototype.tsx`**'s `configurableSlotFor` — when the donor-ship fallback resolves a record and `hp.dormantAllowedComponentEntityClasses` is present, returns a filtered copy of that record (`eligibleComponents`/`eligibleComponentCount` narrowed to the intersection) rather than the donor's own full swap-group list. Absent the field, behavior is unchanged for every other dormant/configurable port in the app.

**Result, live-verified against the real Add-Ship production path on the running dev server:**


Exactly matching SPPV's own finding — one candidate, S3 mount, ready to materialize 2×S2 children.

## 4. Scope note

The restriction is scoped to the Ghost's own dormant port specification only, via the new opt-in `restrictCandidatesToEntityClasses` field — it does not alter the underlying swap group, the donor ship's own compatibility resolution, or any other consumer of `configurableSlotFor`.
