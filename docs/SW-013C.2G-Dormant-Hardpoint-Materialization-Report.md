# SW-013C.2G — Dormant Hardpoint Materialization: Hornet Nose Closure & Fleet-Wide Reconnaissance

**Status:** Complete. Full regression suite 2038/2038 passing, `tsc --noEmit` clean, live Playwright confirmation complete (including a fresh, unambiguous fleet asset for the persistence/revert sequence).
**Commit:** HOLD — awaiting Commander Operational Certification per the work order.

## 1. Root architectural gap

SFM's import pipeline creates a `Port` **only** from an occupied `doc.loadout` entry. Two prior missions (SW-013C.2E/2F, SW-013C.2F Amendment A Finding 4) established that the F7C-S Hornet Ghost Mk II's nose position is not merely a factory-empty instance of the turret-bearing variants' own port — the Ghost's own DataCore export never contains `hardpoint_weapon_nose` in any form, occupied or not. Its nose position is a different, real, physically-present port (`hardpoint_nose_cone`, a Module/Nose Cap) with no analog of the turret variants' own two child weapon mounts. `docs/DormantHardpointMaterializationProposal.md` (SW-013C.2F Amendment A) closed that investigation with an explicit recommendation to defer implementation to its own dedicated mission — this one.

The underlying gap generalizes beyond the Hornet: any ship whose 3D geometry genuinely contains a hardpoint node that ships factory-empty (or, as with the Ghost, doesn't correspond to the loadout-driven port model at all) is architecturally invisible to SFM regardless of how much confirmed compatibility data exists for that exact port name on a sibling variant. This mission builds the first, narrowly-scoped, evidence-gated mechanism to close that gap without weakening the import pipeline's existing "never fabricate" discipline.

## 2. Authoritative Hornet evidence (Objective 1)

Re-confirmed directly against the checked-in raw fixtures and generated data:

1. **Physical existence** — `raw-data/ANVL_Hornet_F7CS_Mk2.json`'s own `root_nmc` geometry-hierarchy export contains a `hardpoint_weapon_nose` node with zero corresponding `loadout` entry. This is the Ghost's own ship-specific evidence, not borrowed from a sibling.
2. **Shape donors** — the identical `hardpoint_weapon_nose` internalName is factory-populated on four other currently-imported F7 Mk II variants (F7A Mk2, F7CM Mk2, F7CM Mk2 Heartseeker, F7 Mk2 Collector Mod), every one of them sharing `canonicalPortType: "WeaponTurret"`, `equipmentGroup: "Weapons"`, `assemblyRole: "DIRECT_WEAPON_MOUNT"`, `minSize`/`maxSize: 3` (`generated-data/ports.json`). Every field on the materialized dormant port is copied verbatim from these real rows.
3. **Compatibility authority** — a confirmed 2-member swap group `ANVL_Hornet_Mk2` (`ANVL_Hornet_F7A_Nose_Turret` / `ANVL_Hornet_F7C_Mk2_Nose_Turret`, `generated-data/configurable-slots.runtime.json`) — the same authority already governing the F7CM Mk2's own real Nose Weapon Mount (SW-013C.2F Objective 1).
4. **Child topology** — weapon-child geometry (2× S3) confirmed via `scripts/generateTurretWeaponSlots.ts`'s own `CONFIRMED_TURRET_ENTITY_CLASSES`, extended in this mission to include `ANVL_Hornet_F7A_Nose_Turret` (confirmed installed on `ANVL_Hornet_F7A_Mk2.json` with 2 real WeaponGun children, both S3 — auto-derived by the generator's own scan, not hand-typed).

**Evidence correction from the earlier proposal document:** the initial evidence pass (recorded in this mission's own `dormantHardpoints.ts` doc comments during development) considered whether the OTHER swap-group member, `ANVL_Hornet_F7C_Mk2_Nose_Turret`, might carry independently-confirmed S2 weapon-slot geometry. Direct inspection found its own `loadout` empty in every raw-data fixture in the corpus — there is no independent size confirmation for it. It is intentionally **not** added to `CONFIRMED_TURRET_ENTITY_CLASSES`; selecting it on the Ghost produces the port itself with zero weapon children. This is documented, not silently absorbed — see §8 (Remaining risks).

## 3. Implementation design (Objective 2)

### The fourth authority: authoritative supplemental topology

Rather than weakening Authority 1 (the import pipeline still only creates ports from real `loadout`/`root_nmc` evidence) or building a second topology merge across generated artifacts, the resolution introduces a narrowly-scoped fourth authority that sits entirely outside the import pipeline: `src/generated/dormantHardpoints.ts`.

- `DormantHardpointSpec` — a small, individually-curated interface (`shipIds`, `internalName`, `displayName`, `positionLabel`, `canonicalPortType`, `equipmentGroup`, `assemblyRole`, `minSize`, `maxSize`, `donorShipEntityClassForCompatibility`, `provenance`).
- `CONFIRMED_DORMANT_HARDPOINTS` — currently exactly **one** entry, the Ghost's Nose Weapon.
- `materializeDormantPorts(shipId, existingPorts): Port[]` — pure, deterministic, dedup-safe: skips any spec whose `internalName` already appears in `existingPorts` (the real imported port silently wins if a future data refresh ever populates it).
- **Injection point** — `src/generated/importedShips.ts`'s `buildView()`: `const shipPorts = [...importedPorts, ...materializeDormantPorts(ship.id, importedPorts)]`. `generated-data/ports.json` is never mutated.

### Identity, provenance, and reconciliation

- Stable canonical id: `${shipId}-dormant-${internalName}` — deterministic, collision-proof against the normalizer's own `-port-` id scheme, never recomputed differently between reloads.
- Two new fields threaded through the full type stack — `Port.isDormant?: boolean`, `Port.dormantDonorShipEntityClass?: string` (`src/engine/types/port.ts`), mirrored on `Hardpoint` (`src/types/index.ts`) and `FactoryHardpointTemplate` (`src/data/shipDefinitions.ts`), and carried through `src/utils/fleetAssetMaterializer.ts` and both branches (matched-row and new-row) of `src/utils/fleetAssetReconciliation.ts`.
- **Critical persistence pattern** — following the same discipline already established for `assemblyRole`/`groupLabel`, `isDormant`/`dormantDonorShipEntityClass` are **never persisted redundantly on a saved Mission-kind `Hardpoint` row**. They are recomputed at prepare/render time by `src/utils/loadoutEditorModel.ts`'s `overlayCanonicalHierarchy(hardpoints, template)`, which joins a saved row back to the current `shipFactoryTemplates` entry by `slotLabel`. This is why a dormant port's marker survives a genuine reload without ever being written to the persisted row itself — the template (derived fresh from `materializeDormantPorts` on every app load) is the single source of truth for the marker.
- **Donor-ship compatibility fallback** — `generated-data/configurable-slots.runtime.json` indexes confirmed swap groups strictly per *occupying* ship; a dormant port's own ship never occupies it, so it can never earn its own entry. `src/pages/ShipWorkspacePrototype.tsx`'s `configurableSlotFor` falls back to `getConfigurableSlotsForShip(hp.dormantDonorShipEntityClass)` when the port's own lookup misses and `hp.isDormant` is true — the same confirmed-group authority, resolved through the ship that actually earned it, never a second compatibility rule.

### Two generic bugs found and fixed in `saveMissionConfiguration` (`src/store/useFleetStore.ts`)

Both surfaced only because a dormant port is genuinely, permanently factory-empty by design — a shape no pre-existing port had ever exercised — but both are generic fixes, not dormant-specific patches:

1. **Materialization guard too strict.** The component-owned-child materialization loop required `row.factoryEntityClass` to be truthy before even considering a row (`if (row.isStructural || !row.factoryEntityClass) continue`). A dormant port permanently has no factory identity, so selecting a real turret on it produced children the UI showed live but `saveMissionConfiguration` rejected outright ("Could not save — ... referenced a port that no longer exists on this ship"). Fixed by relaxing to `if (row.isStructural) continue`; verified via the full regression suite that this is a no-op for every existing port (their own `oldSpec`/`newSpec` still correctly resolve independent of the guard).
2. **Revert-to-empty never marked as a swap.** `swapped = Boolean(finalTargetEntityClass && finalTargetEntityClass !== row.factoryEntityClass)` is always false when reverting a target *to* empty, regardless of what it was targeted at moments before — meaning existing real children from a prior save were never marked stale on a revert-to-empty. This is a **latent, pre-existing gap** that would also have affected the Center Ball Turret pattern once swapped and later reverted; it was simply never exercised because every pre-existing component-owned family always had a real non-empty factory baseline to fall back to. Fixed with a new `droppedToEmpty = previousEffectiveSpec !== null && !newSpec` flag folded into `swapped`, and the early-exit guard relaxed from `if (!oldSpec && !newSpec) continue` to `if (!oldSpec && !newSpec && !previousEffectiveSpec) continue`.

## 4. Ghost Nose Turret Commander workflow (Objective 3)

Selecting either confirmed swap-group member on the Ghost's Nose Weapon row produces:

```
Nose Position
├── F7 Mk II Nose Cap        (real, hardpoint_nose_cone — always valid, independent of the Turret selection)
└── Mk II S3 Nose Turret     (materialized dormant port, hardpoint_weapon_nose)
    ├── Weapon Slot 1 — S3   (independent target)
    └── Weapon Slot 2 — S3   (independent target)
```

- The Nose Cap row is unaffected by any Turret selection — no sibling coupling, confirmed both live and in the permanent suite.
- Mixed, independently-targeted weapons (e.g. an Omnisky IX Cannon in Slot 1 and a Dominance-3 Scattergun in Slot 2) are fully supported — the two child ports carry no coupling to each other.
- Switching Turret → Cap removes both weapon child rows cleanly; switching back to Turret regenerates them with clean (unassigned, `—`) targets — no stale weapon target migrates across the switch.

## 5. Persistence and reconciliation (Objective 4)

The work order's exact required sequence — select Turret, assign two different S2 weapons *(evidence-corrected to S3, see §2)*, save, genuine reload, parent+children survive; then Turret → Cap, save, genuine reload, child rows absent; then Cap → Turret, clean children — is covered end-to-end by `src/pages/__tests__/sw013c2gDormantHardpointMaterialization.test.tsx`'s `"Objective 4's exact required sequence"` test, which drives `useFleetStore.getState().saveMissionConfiguration(...)` directly (never through UI navigation) against a guaranteed-fresh `addFleetAsset('hornet-f7cs-mk2-imported', 'OWNED')` asset, with two real `vi.resetModules()` + re-`import()` reloads in between. All assertions pass, including that a second, independent save reverting the Turret to Intentional Empty produces zero children after the second genuine reload.

Reconciliation (`fleetAssetReconciliation.ts`) resolves the dormant port's identity purely from its stable `internalName`/canonical id — never row position or display label — identical to every other port in the codebase.

## 6. Fleet-wide dormant hardpoint audit (Objective 5)

`scripts/generateDormantHardpointAudit.ts` is a reconnaissance-only script, never imported by app code, producing `generated-data/dormant-hardpoint-audit.json`. Method: diff each ship's own `root_nmc` against its own `loadout`; for every resulting gap, cross-reference the identical `internalName` against every OTHER ship's own occupied use of it (category/size/displayName from `component-metadata-catalog.json`) as a "shape donor," and check `configurable-slots.runtime.json` for a confirmed swap group on any donor ship.

**Noise suppression:** a `PLAYER_RELEVANT_CATEGORIES` allowlist (the union of `PLAYER_USABLE_COMPONENT_TYPES` and `CATEGORY_TO_PORT_TYPE`, plus Turret), a `KNOWN_NON_EQUIPMENT_NODE_PATTERN` regex (antennae/cockpit/seat/decal/light/etc., applied only to the zero-donor bucket), and a frequency ceiling (`NEEDS_INVESTIGATION_SHIP_COUNT_CEILING = 15`) that suppresses fleet-wide system markers recurring on 200+ ships (paint, landing gear, heat sink) — confirmed via direct sampling to be non-equipment.

**Results:**

| Confidence | Count |
|---|---|
| Confirmed (swap group + consistent-category donor(s)) | 31 |
| Probable (consistent category, no confirmed swap group) | 498 |
| Needs Investigation (no donor, or donors disagree) | 3,278 |
| Suppressed as fleet-wide system markers | 1,984 |
| **Total candidates surfaced** | **3,807** |

Per the work order's explicit instruction ("do not automatically activate all candidates merely because the generic mechanism exists"), **none** of these were implemented in this pass. `docs/Roadmap.md`'s new ARCH-009 entry captures the highest-evidence candidates (the Idris-P's nose railgun mount, the Hornet F7C/Wildfire's own center-nose mount) for a future, individually-evidenced mission.

**Honest limitations of the audit, stated plainly:**
- The audit's own blind cross-fleet matching produced a **false negative** for the very case this mission implements: the Ghost's own `hardpoint_weapon_nose` scored only "Needs Investigation," not "Confirmed," because its donor set includes an unrelated Vanduul Mauler S10 cannon alongside the real Hornet-family turret donors, and the generic scorer doesn't disambiguate. The Ghost was only correctly elevated to Confirmed through additional manual narrowing (restricting to the Hornet-specific swap group) that the generic audit does not perform automatically.
- The "Confirmed" tier itself carries genuine **false-positive risk** — e.g. the Asgard's `hardpoint_weapon_wing_left`/`_right` mixes a Valkyrie remote-turret donor with an unrelated family of VariPuck gimbal mounts that happen to share the same internalName across unrelated ship families.
- **Conclusion recorded for future missions:** the audit is a triage tool requiring per-candidate human review against this mission's own four-point evidence standard — never an auto-truth source, and never a basis for batch activation.

## 7. Safety boundaries (Objective 6)

All actively enforced by the implementation, not merely documented:
- **No duplicate port** — `materializeDormantPorts`'s own dedup check against `existingPorts` (verified by a dedicated test).
- **No blanket category exposure** — compatibility is gated by the same confirmed-swap-group authority every other port already uses (`configurableSlotFor`'s donor-ship fallback), never a size/category match.
- **Vessel-bound compatibility unweakened** — `vesselBoundTags` gating (SW-013C.2F Amendment A) applies identically to a materialized dormant port's target selection.
- **No inventory mutation, no factory-loadout inflation** — a dormant port permanently carries no `factoryItemId`/`factoryEntityClass`; it is readiness-neutral until a Commander explicitly targets it, and never appears occupied by default (confirmed live and in the permanent suite).
- **Distinguishable state** — `isDormant: true` is present on the `Hardpoint` object everywhere the app needs to distinguish Factory-installed / Commander-installed / Target-selected / physically-available-but-dormant.

## 8. Dropdown collision fix (Objective 7)

`src/components/TargetComponentPicker.tsx` — the single shared component every "New Target"/"Change Installed" picker in Ship Workspace already renders through, so this fix applies generically, not to the Hornet Nose control specifically.

- Added `inputRef`/`listboxRef` and a `useLayoutEffect` that measures the real input's `getBoundingClientRect()` against `window.innerHeight`/`innerWidth` on open, on every filter-length change, and on window resize/scroll (capture phase).
- Computes `menuPlacement` (`{top?, bottom?, left, width, maxHeight}`): opens downward when there's at least `MIN_USABLE_HEIGHT` (120px) of room below, or more room below than above; flips upward otherwise. `maxHeight` is capped to the real available space in whichever direction was chosen (up to a `PREFERRED_MAX_HEIGHT` of 256px), so the list is internally scrollable rather than ever running off-screen.
- The listbox itself is rendered via `createPortal(..., document.body)` with `position: fixed`, so no ancestor table/sticky-layer `overflow`/stacking context can clip it.
- Blur handling updated to check both `containerRef` and the new `listboxRef`, so keyboard focus moving into a portaled option is still recognized as "inside this picker."
- Live-verified: a combobox scrolled to the bottom of a tall ship's loadout tree (1400×900 viewport) renders its open listbox fully inside the viewport (`listboxY: 784.6`, `listboxBottom: 858.6`, both within the 900px viewport height).

**Test-suite migration cost:** portaling broke the `input.closest('div')!.querySelector('[role="listbox"]')` pattern used across 6 test files (37 occurrences), since the listbox is no longer a DOM descendant of the input's container. Fixed mechanically via `document.getElementById(x.getAttribute('aria-controls')!)` (an earlier attempt using a bare `#id` CSS selector broke on real ids containing spaces, e.g. `"catalog-Left Top Missile Rack-missile-aggregate-listbox"`).

## 11. Remaining risks

- **`ANVL_Hornet_F7C_Mk2_Nose_Turret` (the other swap-group member) has no independently-confirmed weapon-slot geometry.** Its own `loadout` is empty in every raw-data fixture in the corpus. Selecting it on the Ghost currently produces the port itself with zero weapon children — a documented, honest gap, not a crash, covered by its own regression test.
- **The fleet-wide audit is a triage tool, not an activation list.** Its blind cross-fleet matching has both a confirmed false negative (this mission's own Ghost case) and confirmed false-positive risk (the Asgard wing-mount example, §6) baked into its method. Any future activation from `docs/Roadmap.md`'s ARCH-009 candidates requires its own individual four-point evidence review and dedicated test coverage — the audit only narrows where to look.
- **The two generic `saveMissionConfiguration` fixes (§3) widen behavior for every component-owned-child port in the codebase**, not just the dormant one. Both are covered by the full regression suite (including the pre-existing Center Ball Turret pattern, explicitly re-verified unaffected), but any future component-owned-child port family should be aware the revert-to-empty path now correctly clears stale children where it previously did not.
